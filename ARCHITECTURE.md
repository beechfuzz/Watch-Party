# Architecture Decisions

This document records material architectural decisions made while building Watch Party, the alternatives considered, and why each was chosen. It is written incrementally, in build order, starting with the Emby investigation the project spec required before any Emby integration code was written.

---

## 0. Emby API investigation (Phase 0)

**Method.** The project spec calls for a live, throwaway proof-of-concept against a real Emby server before writing any integration code. The development sandbox this project was built in has an egress allowlist that does not include the operator's Emby server, so a live POC could not be run from here. With the operator's agreement, this investigation was done instead by researching Emby's own wiki documentation (`github.com/MediaBrowser/Emby/wiki`) and, for anything the wiki doesn't spell out at the wire-protocol level, cross-checking against Jellyfin's server source. Jellyfin was forked from Emby's last open-source snapshot in 2018 and still carries an explicit "legacy Emby" compatibility branch in its auth layer (`AuthorizationContext.cs` literally parses an `"Emby ..."` authorization scheme, and Jellyfin's internal namespace is still `Emby.Server.Implementations` in places) — so it's a reasonable corroborating source for the parts of the API that predate the fork, but **it is Jellyfin source, not Emby source**, and every finding below is marked with how it was confirmed.

**This is real risk, not a formality: treat every endpoint shape below as unverified until it's been exercised against the operator's actual Emby server**, and re-confirm before relying on any of this in production. The one item that could not be reduced to \"high confidence\" at all — CORS — is called out specifically in §0.4 with a concrete first thing to test.

### 0.1 Authentication — `POST /Users/AuthenticateByName`

- Requires an `X-Emby-Authorization` header identifying the client even for this call: `X-Emby-Authorization: Emby Client="Watch Party", Device="<device name>", DeviceId="<stable uuid>", Version="<app version>"`. Confirmed via the Emby wiki's User Authentication page and, at the code level, Jellyfin's `AuthorizationContext.cs` (these fields are copied verbatim onto the resulting session).
- Body: `{"Username": "...", "Pw": "..."}` — plaintext password, field name `Pw` not `Password`. (An old wiki revision described legacy SHA1/MD5 password-hash fields; those were retired well before this project's timeframe and are not used here.)
- Response: `{"User": {...}, "SessionInfo": {...}, "AccessToken": "...", "ServerId": "..."}`. Confirmed at the code level via Jellyfin's `AuthenticationResult` model, corroborated by the wiki's description of the response.
- The `AccessToken` is long-lived and reusable (not single-request scoped) — used on every subsequent call until logout or server-side revocation, at which point Emby returns 401 and the client must re-authenticate. This lines up with the spec's requirement to invalidate the local session (forcing reauthentication) rather than silently retrying a dead token.
- Token is sent on subsequent requests either as an `X-Emby-Token` header, or as an `api_key` (or `ApiKey`) query parameter. Both are accepted; confirmed via the wiki's API Key Authentication page and Jellyfin's auth parsing code.

**Decision:** Watch Party proxies the raw credentials directly to this endpoint, discards the plaintext password immediately after the call returns, and stores only the returned `AccessToken` (encrypted at rest — see §1.3). Confidence: high.

### 0.2 Playback URL mechanism — the crux of the "no proxy" design

**`GET/POST /Items/{itemId}/PlaybackInfo`** — call this first for any item about to be played. Response is `{"MediaSources": [...], "PlaySessionId": "...", "ErrorCode": ...}`. Each `MediaSourceInfo` entry has `Id`, `Container`, `SupportsDirectPlay`, `SupportsDirectStream`, `SupportsTranscoding`, `TranscodingUrl` (only populated for the transcode case), among others — **there is no `DirectStreamUrl` field**; for direct play/stream the client is expected to construct the URL itself. Confirmed at the code level via Jellyfin's `MediaSourceInfo` model; consistent with the Emby wiki, which also documents manual URL construction rather than a server-provided direct-stream URL.

**Direct Play / Direct Stream URL** (client-constructed):
```
GET /Videos/{itemId}/stream[.{container}]?Static=true&MediaSourceId={mediaSourceId}&PlaySessionId={playSessionId}&api_key={AccessToken}
```
`Static=true` tells Emby to serve the source file as-is instead of transcoding. The `api_key` query parameter is what makes this usable from a plain HTML `<video src>` — a video element cannot set custom headers, so query-string auth is the only viable mechanism for this specific request. Confirmed via the wiki's Video Streaming page; query-param auth confirmed at the code level via Jellyfin's `AuthorizationContext`.

**Transcoded / HLS URL** (client-constructed):
```
GET /Videos/{itemId}/master.m3u8?MediaSourceId={mediaSourceId}&PlaySessionId={playSessionId}&DeviceId={deviceId}&api_key={AccessToken}
```
Confirmed at the code level via Jellyfin's `DynamicHlsController`. Segment and key URLs emitted inside the playlist are relative and are expected to inherit the same query-string auth the playlist request carried — this specific detail is **not explicitly documented anywhere reachable during this investigation** and is rated medium confidence / inferred from how every Emby/Jellyfin web client actually behaves in practice, not from a citable spec. **Verify this first** against the operator's server: request `master.m3u8` with a valid `api_key`, and confirm the segment URLs inside the returned playlist are directly fetchable without additional auth.

After playback ends, `DELETE /Videos/ActiveEncodings?DeviceId={deviceId}` releases the server-side transcode job.

**`PlaySessionId`**: prefer the one returned by `PlaybackInfo`, since the server uses it to track and later cancel transcode jobs. The wiki allows a client-generated random string as a fallback, but there's no reason to use the fallback path here since Watch Party always calls `PlaybackInfo` first.

**Range requests:** confirmed supported on the static/direct-stream endpoint — Jellyfin serves it via `PhysicalFileResult { EnableRangeProcessing = true }`, the standard ASP.NET Core mechanism for `Range:`/`206 Partial Content` handling, which is exactly what a `<video>` element needs for native seeking. Rated high confidence for Emby by inference (Emby's server is also ASP.NET Core-based and shares direct lineage with this part of Jellyfin's stack) but not directly confirmed against Emby's closed-source binary.

**Decision:** the browser's `<video>` element is pointed directly at the constructed stream URL (Direct Play/Stream case) or handed to an HLS player against the `master.m3u8` URL (transcode case), both carrying the requesting user's own `api_key`. Watch Party's server never touches the media bytes — consistent with the spec's non-negotiable "no proxy" requirement. Confidence: high for the URL shapes and auth mechanism; medium for HLS segment auth inheritance (flagged above for live verification).

### 0.3 Per-user Emby playback reporting

`POST /Sessions/Playing`, `POST /Sessions/Playing/Progress`, `POST /Sessions/Playing/Stopped` all take the same JSON body shape: `ItemId`, `MediaSourceId`, `PositionTicks`, `IsPaused`, `PlayMethod` (`"DirectPlay" | "DirectStream" | "Transcode"`), `PlaySessionId`, among other optional fields. Confirmed via the Emby wiki's Playback Check-ins page, independently corroborated by Jellyfin's `PlaystateController` source (field-for-field match, strong corroboration since this endpoint predates the 2018 fork). Auth is the ordinary `X-Emby-Token` header — these are server-to-server-style calls made from Watch Party's backend using each participant's own token, not constrained by the `<video>` tag's inability to set headers. Confidence: high.

### 0.4 CORS — the one real open risk

Emby's own documentation site (`dev.emby.media`) and community forums were unreachable from the research environment (network policy), so **this is the one area of this investigation that is not confirmed against any Emby-authored source** — only forum thread *titles* suggesting other operators have hit CORS issues in front of Emby and worked around them via reverse-proxy configuration (nginx), and a code-level look at Jellyfin's CORS handling (which defaults to wildcard `Access-Control-Allow-Origin: *` unless the admin configures specific allowed hosts — a Jellyfin behavior, not a confirmed Emby one).

One relevant data point: an existing open-source project solving the same problem (`Oratorian/emby-watchparty`) chose to fully proxy Emby traffic through its own backend specifically to avoid browsers talking to Emby directly at all. That is a deliberate rejection of the architecture this spec requires, made by another team building the same kind of tool — worth taking seriously as a signal, but per the spec's explicit instruction, Watch Party is not adopting a media-proxying architecture; the operator has already accepted that trade-off and stated the reasoning (Emby's own uptime shouldn't become Watch Party's problem, and reimplementing Range/HLS-manifest passthrough is exactly the complexity this project is trying to avoid).

**Decision:** proceed with direct browser-to-Emby streaming as specified, but treat CORS as an explicit deployment prerequisite rather than an assumption:
- Because Watch Party authenticates Emby requests via the `api_key` query parameter (not cookies), the browser does not need to send credentials cross-origin for media requests — so the required CORS policy is the simple, non-credentialed kind (`Access-Control-Allow-Origin` naming the Watch Party origin, or `*`), not the more complex `Access-Control-Allow-Credentials: true` case that trips up cookie-based setups.
- The README documents the concrete Traefik middleware configuration needed to add these headers in front of Emby, since Emby's own CORS support could not be confirmed as sufficient (or even present) from this investigation.
- **First thing to test once the operator has live access:** load the constructed Direct Play URL in a `<video>` tag served from the Watch Party origin and check the browser console for CORS errors, before building anything else on top of it. If Emby's default behavior turns out to already be permissive (wildcard, like Jellyfin's default), the Traefik middleware becomes a no-op layer of defense-in-depth rather than a hard requirement — but that can only be confirmed live.

## 1. Library and implementation choices

The spec leaves several implementation details to be decided at build time, explicitly stating they don't materially affect architecture. Decisions:

### 1.1 WebSocket library: `nhooyr.io/websocket`
Chosen over `gorilla/websocket` (both were offered as options). `nhooyr.io/websocket` has a smaller API surface, is context-aware throughout (fits idiomatic use of `context.Context` for cancellation/deadlines alongside the rest of this codebase), and has no dependency on the older `x/net` websocket internals gorilla still carries. Gorilla is more widely deployed and would have been an equally reasonable choice; this was a coin-flip-with-a-slight-preference, not a decision with real stakes.

### 1.2 Migration tool: `golang-migrate/migrate` (not hand-rolled)
The spec allows either `golang-migrate` or a minimal hand-rolled runner. `golang-migrate`'s `database/sqlite` driver package imports `modernc.org/sqlite` directly (confirmed by inspecting its import graph) rather than the CGO-based `mattn/go-sqlite3` driver some might expect — so using it does not compromise the no-CGO/static-binary requirement. Given that, there was no reason to hand-roll a runner: versioned up/down SQL files, embedded via `embed.FS` and the `iofs` source driver, is exactly the "minimal reasonable implementation" the spec asks for when a decision doesn't materially matter.

### 1.3 Token-at-rest encryption: AES-256-GCM
`TOKEN_ENCRYPTION_KEY` (32 bytes, base64 or hex) is used directly as an AES-256 key; each encrypted value is `nonce (96 bits, random per call) || ciphertext || GCM tag`, base64-encoded for SQLite TEXT storage. AES-GCM was chosen over a non-authenticated mode because it detects tampering/corruption on decrypt (returns an error) rather than silently producing garbage that would then be sent to Emby as a bearer token.

### 1.3.1 CSRF coverage and where "join" fits

The spec lists join among the state-changing actions needing CSRF protection. In this implementation, joining a party is not a separate HTTP endpoint — it happens as part of the WebSocket handshake itself (`GET /ws/parties/{id}`), which re-validates the user's media authorization and is protected by Origin validation instead (browsers don't attach custom headers to a WebSocket upgrade the way a synchronizer token would need, so Origin checking — already required by the spec for this endpoint — is the applicable defense here, not CSRF). Every other state-changing action the spec calls out (create party, transfer host, end party, logout, leave) is a regular JSON POST and does carry the CSRF header requirement.

### 1.4 CSRF: synchronizer token, not double-submit-cookie
The spec explicitly says not to introduce a `SESSION_SECRET` unless something actually needs signing, and that CSRF may need its own key only if a double-submit-cookie (HMAC-based) pattern is used. Since sessions are already server-side and opaque, Watch Party generates a second random 256-bit token at session-creation time, stores it alongside the session row, and requires it to be echoed back in an `X-CSRF-Token` header on every state-changing request (compared with a constant-time comparison). This needs no signing key at all — one fewer secret to manage — and is exactly as strong as a synchronizer token is expected to be, since the token is bound server-side to the session rather than derived from anything guessable.

### 1.5 Session timestamps: RFC3339Nano wall-clock, not monotonic
Per the spec's own guidance: Go's monotonic clock reading is stripped once a `time.Time` is serialized, so a `server_timestamp` sent over the WebSocket as RFC3339Nano text is a wall-clock value, not a monotonic guarantee. This project accepts that as a deliberate, documented simplification — sub-second drift thresholds and typical NTP slewing behavior mean the rare wall-clock adjustment does not meaningfully break the sync experience — rather than building a custom monotonic-timestamp wire format just to sidestep a JSON-serialization detail. The same RFC3339Nano text format is reused for all other stored timestamps (session expiry, party creation, etc.) purely for consistency and human-readability in the database; those have no monotonicity requirement to begin with.

### 1.6 Sync math: implemented once in Go, mirrored (not shared) in the browser client
The frontend is vanilla JS with no bundler, so there is no mechanism to share code with the Go backend across that boundary. Clock-offset estimation, expected-position/drift calculation, and the rate-nudge-vs-hard-seek decision are implemented as pure, thoroughly unit-tested functions in `internal/syncalg`, which serves as the canonical reference and is also what the server itself uses for its debug-level sync diagnostics logging. The same algorithm is re-implemented in `web/static/js/sync.js` for the browser, since only the browser can actually drive a `<video>` element's `playbackRate`. This is intentional, acknowledged duplication of a small, stable algorithm — not an attempt to avoid it — because the alternative (a build step to share code, or a WASM bridge) would be a disproportionate amount of tooling for ~150 lines of arithmetic, and would cut against the spec's "no frontend build pipeline" constraint.

### 1.7 Static assets are served `Cache-Control: no-cache`, always

A consequence of §1.6's "no build pipeline" constraint: static assets have no content hash in their filename (`player.js` is always `/static/js/player.js`, deploy after deploy), so a new deploy overwrites a given URL's content in place rather than shipping under a new URL. Go's `http.FileServer` over an embed.FS sends no cache-lifetime header of its own — which is exactly the condition under which some CDNs (Cloudflare's default cache level among them) apply their own heuristic caching by file extension, independent of whatever the origin did or didn't send, and independent of the browser's own cache. A live deployment hit this directly: two player.js fixes appeared to "not work" after being merged and deployed, because a stale pre-fix copy was still being served from a cache neither this app nor its immediate reverse proxy controlled. `registerPages` now sets `Cache-Control: no-cache` on every static asset and every server-rendered page — not `no-store` (still permits storing) but requiring revalidation before reuse, which most CDNs honor as an explicit override even when their extension-based heuristics would otherwise apply. This fixes future deploys; a stale copy already sitting in a CDN's edge cache from before this shipped still needs a one-time manual purge.

## 2. Session implementation

Opaque, cryptographically random 256-bit session ID (hex-encoded), stored `HttpOnly` and `SameSite=Lax` always, `Secure` whenever the issuing request looks like it arrived over HTTPS. The session ID is looked up server-side in SQLite on every request; no JWT, no signing secret. The Emby `AccessToken` itself lives on the `users` row (encrypted, see §1.3), not on the session — a user's token is refreshed in place on each login, and multiple concurrent sessions for the same user share it, which matches how Emby tokens actually work (they're not scoped to a single Watch Party session).

Two independent expiry mechanisms, both configurable: an idle timeout (`SESSION_IDLE_TIMEOUT`, sliding — refreshed on each authenticated request) and an absolute max age (`SESSION_MAX_AGE`, fixed at session creation). Either one being exceeded invalidates the session. If Emby itself rejects the stored token (401 on any Emby call made on the user's behalf), Watch Party deletes all of that user's sessions server-side and forces re-authentication, rather than retrying a dead token indefinitely.

### 2.1 Secure-cookie determination: per-request, not a `DEV_MODE` flag

**Original design, and why it changed.** The first version of this app decided whether to set the `Secure` cookie attribute from a single, deployment-wide `DEV_MODE` boolean: `Secure` unless `DEV_MODE=true`, which was meant only to unblock local `http://` testing. That design has a real gap it didn't account for: a legitimate self-hosted deployment can be reachable at more than one origin simultaneously with *different* schemes — e.g. an external `https://watchparty.example.com` through a reverse proxy, and an internal-only `http://watchparty.home` on the operator's own LAN that has no TLS certificate and doesn't need one. Under the old design there was no way to serve both correctly: `DEV_MODE=false` makes every cookie `Secure`, which a browser will silently refuse to store when the page was loaded over the HTTP origin (login appears to succeed but the session never persists); `DEV_MODE=true` makes every cookie non-`Secure`, weakening the HTTPS origin's cookie for no reason, directly contradicting the spec's own instruction not to relax the production requirement to accommodate this. A static, deployment-wide flag simply cannot get both origins right at once, because "is this cookie allowed to be `Secure`" is a property of the individual request, not of the deployment.

**Fix:** `Secure` is now computed per-request (`internal/session.isSecureRequest`): true if `r.TLS != nil` (this process is terminating TLS itself — not the normal case here) or the request carries `X-Forwarded-Proto: https` (the standard signal a reverse proxy sets, and the normal case for this project's documented Traefik-fronted deployment). This makes `DEV_MODE` unnecessary for its original purpose too: a bare `go run ./cmd/server` hit directly over `http://localhost:8080` has no `X-Forwarded-Proto` header at all, so it's indistinguishable from — and handled identically to — the internal-LAN-origin case, with zero configuration.

**Trust assumption, stated explicitly.** `X-Forwarded-Proto` is attacker-controllable input if the process is ever directly reachable by an untrusted client rather than strictly through the reverse proxy it's designed to sit behind. This is judged acceptable, not a new risk introduced by this change: the project's whole deployment model already assumes Watch Party is not directly internet-reachable (`docker-compose.yml` puts it on an internal Traefik network with no published port; `watchparty.container`'s example binds `PublishPort` to `127.0.0.1` only), and a forged header here can only make the server treat a request as *more* secure than it is — which a real browser would simply refuse to honor by declining to store the resulting `Secure` cookie — not less, so it cannot be used to downgrade a genuinely-HTTPS session's cookie.

`APP_ORIGINS` no longer rejects non-`https://` entries the way it used to (that check existed purely to prevent a `DEV_MODE`-style global weakening; it no longer applies to anything). A non-HTTPS entry now just produces an informational startup log line, since it's an intentional, supported configuration rather than a mistake to guard against.

## 3. WebSocket protocol design

One WebSocket connection per client; one server-side broadcast hub per active party, implemented as an actor: each party is a single goroutine reading from a buffered command channel, so all state mutation for a given party is inherently serialized without needing a mutex around the playback state itself (a `map[partyID]*Party` registry, guarded by a small mutex, exists only for looking up/creating/removing party actors — not for the state inside them). This was chosen over a plain mutex-guarded struct because the correctness property that matters most here — commands for one party are applied in a strict, well-defined order, with sequence numbers assigned exactly once — falls out for free from a single-threaded actor, whereas a mutex-guarded struct would need equal care taken by hand at every call site to get the same guarantee.

Every message carries a `protocol_version` field (see `internal/wsproto`). Messages are grouped into three categories, kept conceptually and structurally distinct:
- **Control events** (host-only, authoritative): `play`, `pause`, `seek`, `host_transfer`. These are requests — the server validates host authorization, timestamps and sequences the resulting state change, applies it to the in-memory party state, and broadcasts the result. The broadcast, not the request, is what every client (including the host's own) treats as authoritative.
- **Lifecycle events**: `join`, `leave`.
- **Transport/control frames**: `ping`/`pong`/`heartbeat`, `clock_sync`, `snapshot`.

Every authoritative state update (every control-event broadcast, and every `snapshot`) carries the same four fields: `position_ticks`, `is_playing`, `server_timestamp`, `sequence_number`. `sequence_number` is a per-party counter, incremented exactly once per applied state change by the single-threaded party actor; clients reject any update whose sequence number is not strictly greater than the last one they applied (`internal/syncalg.IsStale`), which is what prevents a delayed `seek` from clobbering a newer `play`, or a stale snapshot from undoing a fresher one.

## 4. Synchronization algorithm

See `internal/syncalg` (canonical, unit-tested implementation) and §1.6 above for why the same math is mirrored in the browser client.

- **Clock offset / RTT**: standard two-timestamp estimator using the client's `t0`/`t3` and the server's echoed `t1`/`t2` — `RTT = (t3-t0) - (t2-t1)`, `offset = ((t1-t0) + (t2-t3)) / 2`. More accurate than assuming one-way latency is simply `RTT/2`.
- **Expected position**: `authoritative_position + (server_now - authoritative_timestamp)` while playing, where `server_now = local_now + clock_offset`; simply `authoritative_position` while paused (time doesn't advance).
- **Drift correction**: drift below `SYNC_SOFT_DRIFT_MS` → no correction. Between soft and `SYNC_HARD_DRIFT_MS` → nudge `playbackRate` (magnitude scales with how far into that range the drift falls, capped at `SYNC_MAX_RATE_ADJUSTMENT`), which avoids a visible jump; once drift falls back under the soft threshold, rate returns exactly to `1.0` rather than lingering off-speed. Beyond the hard threshold → hard seek, since a rate nudge would take too long to catch up. All three thresholds plus the snapshot interval are environment-configurable, not hardcoded.

## 5. Browser playback strategy

The video element's `src` (Direct Play/Stream) or HLS player source (transcoded) is constructed per §0.2, using the viewing user's own `AccessToken` as an `api_key` query parameter — never a shared service token. Client-generated player events that were themselves caused by a server-issued sync command (e.g. the `<video>` element firing its own `play` when the client called `.play()` in response to a broadcast) are suppressed from being re-sent to the server as new commands, using a short-lived "expecting this event" flag set immediately before the programmatic call and cleared once the corresponding native event fires — this is what prevents a feedback loop between server-driven state changes and the browser's native media element events.

### 5.1 Two real bugs found via a live deployment, and the fix

A real user's first playback attempt failed instantly with the browser's generic `MEDIA_ERR_SRC_NOT_SUPPORTED` ("was not suitable"). Two separate, compounding bugs were responsible:

**Bug 1 — JSON casing mismatch.** `emby.PlaybackURLResult` had no JSON struct tags, so it serialized with Go's default field names: `{"URL": ..., "IsTranscoded": ...}`. `player.js`, written against the intended snake_case convention the rest of this API uses, read `playback.url` (lowercase) — `undefined`, for every single login, regardless of the item's format. `video.src = undefined` becomes the literal string `"undefined"`, which the browser correctly rejects. This alone explained the reported symptom. Fixed by adding explicit `json:"url"`, `json:"is_transcoded"`, etc. tags, and by pinning the wire shape with a dedicated test (`TestPlaybackURLResult_WireCasingMatchesFrontend`) — a Go-side unit test alone couldn't have caught this, since the Go code was internally consistent (struct field access on the Go side always worked); only a test that round-trips through actual JSON and checks the keys a JS reader would use catches this class of bug.

**Bug 2 — no device capability negotiation.** `GetPlaybackURL` called `PlaybackInfo` with a plain `GET` and no `DeviceProfile`. Without one, Emby has no idea it's being asked on behalf of a browser and returns `SupportsDirectStream`/`SupportsDirectPlay` based on raw server capability — "can I serve these bytes as-is" — which is almost always yes, including for containers like `.mkv` that no browser's `<video>` element can open at all, regardless of the codec inside. The fix switches to `POST /Items/{id}/PlaybackInfo` with a `DeviceProfile` describing what a generic modern browser can actually decode natively (conservatively: H.264/AAC in MP4, VP8/VP9/AV1/Opus in WebM), routing everything else through an HLS transcoding profile — the same mechanism every real Emby/Jellyfin web client uses. This is the correct, Emby-native way to make this decision, rather than trying to reimplement container/codec sniffing client-side.

That second fix has a consequence: transcoded output is always HLS (`.m3u8`), which only Safari plays natively in a `<video>` element. Chrome, Firefox, and Edge need a JS demuxer feeding Media Source Extensions. **hls.js** (Apache-2.0) is vendored as a pre-built, non-module `<script>` (`web/static/js/vendor/hls.min.js` — see `vendor/README.md`) rather than pulled in via a package manager at build time, consistent with this project having no frontend build pipeline (§1.6): `player.js` feature-detects native HLS support (`video.canPlayType(...)`) and only invokes `Hls` when the browser actually needs it, so Safari's path is unaffected.

**Also fixed while in the area:** when Emby's `PlaybackInfo` response includes its own `TranscodingUrl` for the transcode case (it does, once a `DeviceProfile` is supplied), that URL is now used verbatim (host-prefixed, `api_key` appended) instead of hand-constructing a `master.m3u8` URL from scratch — more robust, since Emby's own URL already carries whatever parameters its transcoding pipeline actually needs for that specific negotiation.

### 5.2 A third bug, from the same deployment: one Emby base URL was doing two jobs

After §5.1 shipped, the same deployment hit a new failure: hls.js immediately reported `manifestLoadError` — it couldn't fetch the `.m3u8` manifest at all. The cause was `emby.Client` using a single `baseURL` for two purposes that need different values whenever Emby is reached over an internal address:

- **Server-to-server calls** (`AuthenticateByName`, `PlaybackInfo`, progress reporting) — these can and, per this same deployment's earlier hairpin-NAT fix (Emby and Watch Party sharing a Podman network, `EMBY_SERVER_URL=http://emby:8096`), *should* use an address only this server can reach.
- **Browser-facing playback URLs** (the direct-stream/HLS URL handed to `<video>`/hls.js) — these are fetched by the participant's own browser, which has no way to resolve container-internal DNS like `emby:8096`. hls.js's manifest fetch failed for exactly this reason: it was trying to load a manifest URL the browser's network stack couldn't even look up.

`GetPlaybackURL` built both kinds of URL from the same `baseURL`, so fixing reachability for one direction (server → Emby) broke reachability for the other (browser → Emby) — the two requirements are in direct tension, and a single config value can't satisfy both once Emby is only reachable from the server via an internal address.

The fix splits them: `emby.Client` gained a second `publicBaseURL`, defaulting to `baseURL` (so nothing changes for deployments where both are already reachable from everywhere), overridable via `SetPublicBaseURL` — wired to a new `EMBY_PUBLIC_URL` config variable. `GetPlaybackURL` now builds the direct-stream URL, the Emby-provided `TranscodingUrl`, and the hand-built `master.m3u8` fallback from `publicBaseURL`; every other Emby call still uses `baseURL`. See README.md's "Internal vs. public Emby address" section for the operator-facing explanation.

### 5.3 A fourth bug, from the same deployment: a duplicated `api_key` query param

§5.2's fix got the HLS manifest URL reachable, but the same deployment then hit a `401` fetching it — this time with CORS working correctly (confirmed via the browser's network inspector: the actual GET reached Emby and got a same-origin-correct response, just with a `401` status). The request URL, inspected directly, had **two** `api_key` query parameters with the same value.

The cause: Emby's `PlaybackInfo` response often returns a `TranscodingUrl` that already has its own `api_key` embedded — from whichever token authenticated that `PlaybackInfo` call. `GetPlaybackURL`'s handling of the Emby-provided `TranscodingUrl` case (added in §5.1's fix) assumed it never carried one, and unconditionally appended `&api_key=<token>` regardless. When Emby's URL already had one, the wire request ended up with `...&api_key=X&api_key=X`. Emby's query-parameter binding apparently can't reconcile two values for the same key into a single valid token, and rejects the request outright rather than picking one — hence the `401`, with the CORS layer never even coming into play since the request itself was well-formed enough to reach Emby and get a real (if rejecting) response.

Fixed by parsing the Emby-provided `TranscodingUrl`'s query string and overwriting `api_key` (via `url.Values.Set`, which replaces rather than appends) instead of string-concatenating one on. This has a secondary benefit: it guarantees the final URL always carries the *requesting user's own* token, not whatever token happened to authenticate the `PlaybackInfo` call — in practice these are the same token today, but the fix no longer depends on that coincidence holding.

### 5.4 A fifth bug, from the same deployment: transcode sessions always started at position 0

Once playback itself worked, the deployment reported a specific pattern: the host (on their internal network) saw playback start normally, but a guest joining afterward (on a mobile connection) didn't see their video start for almost a minute.

The cause: `GetPlaybackURL` never told Emby where in the item to start transcoding — every transcode session began at position 0, regardless of where the party actually was. The client then relied entirely on its own client-side `video.currentTime = expected` seek (`applyAuthoritativeState`'s `hardSeek`) to jump to the real position once the manifest loaded. For a transcoded (HLS) stream, that "seek" isn't a cheap `Range` request against a static file the way direct-stream/play is — hls.js requesting a segment at a given time offset requires Emby's transcoder to actually have encoded up to that point first. Joining a party that's already, say, 10 minutes in meant Emby had to transcode through those 10 minutes — decode-and-discard, or a slow non-keyframe-accurate seek — before it could produce the segment the client asked for. The host, who started the transcode at (or near) position 0 in the first place, never hit this path; anyone joining significantly later did, and the wait scaled with how far into the item the party already was.

Fixed by passing the party's actual current position to Emby up front, via `StartTimeTicks` in the `PlaybackInfo` request body (and mirrored onto the hand-built `master.m3u8` fallback's query string) — this is the same mechanism Emby's own web client uses for a user-initiated seek: rather than requesting from 0 and seeking client-side afterward, request a transcode session that begins at the target offset directly, so Emby can start close to (ideally at) the right keyframe from the outset.

That position has to be the *live*, extrapolated one — not the raw `PositionTicks` last written to `party.State`, which goes stale the instant playback continues past it. `party.Party` gained `CurrentPositionTicks()`, running the same `syncalg.ExpectedPosition` extrapolation the client uses (elapsed time since the last state change, added to the last known position, only while playing) but server-side with no clock offset to correct for. `handlePlaybackURL` calls this (via the live `Hub`-held actor, not the DB) immediately before requesting the playback URL.

**This has a real consequence for the client, not just Emby:** Emby's transcoded HLS output for a session that starts mid-item resets its own timeline to 0 — the first segment's timestamps begin at (approximately) zero, not at the real item offset, exactly like what happens when Emby's own web client performs a seek (which is implemented as: throw away the current transcode session, request a new one with `StartTimeTicks` set to the seek target, and treat the resulting stream as starting fresh at 0). A client that kept doing `video.currentTime = <absolute item position>` against a stream whose local timeline no longer starts at 0 would seek to the *wrong place* — potentially past the end of what that session's manifest even covers.

So `PlaybackURLResult` gained `StartPositionTicks` (0 for direct play/stream, since that timeline genuinely is absolute; the requested offset for a transcoded session), and `player.js` now tracks it as `playbackOffsetTicks`, with every position conversion going through two small helpers — `itemPositionTicks(videoSeconds)` and `videoSeconds(itemTicks)` — instead of a bare `* TICKS_PER_SECOND` on `video.currentTime`. Every call site that used to do that conversion directly (`applyAuthoritativeState`'s hard seek, the drift loop's actual-vs-expected comparison, `sendControl`, the clock-sync ping) goes through these instead. For direct play/stream, `playbackOffsetTicks` is 0 and both helpers are the identity conversion — unchanged behavior.

This assumption (mid-item transcode sessions reset to a 0-based timeline) matches Emby/Jellyfin's well-documented seek pattern, but wasn't verified against this specific deployment's Emby version at fix time — worth confirming empirically (does a guest joining late land at the correct point in the video, immediately, without a stray hard-seek loop?) rather than taking on faith.

### 5.5 Player UI gaps found by the same round of real-world use

Three smaller issues surfaced once playback itself was reliable:

- **The "Start Playback" overlay could get stuck visible over already-playing video.** It was only ever hidden by the start button's own click handler — nothing hid it if playback began some other way (e.g. an autoplay attempt succeeding on a later authoritative state after an earlier one had been blocked, which is exactly when the overlay gets shown in the first place). Fixed with a `video.addEventListener("playing", ...)` handler that hides it unconditionally whenever the video actually enters the playing state, regardless of what caused it — this can't drift out of sync with reality the way hiding it per-code-path could.
- **No fullscreen affordance.** Added a dedicated Fullscreen button (`video.requestFullscreen()`, with a `video.webkitEnterFullscreen()` fallback for iOS Safari, where only the `<video>` element itself — not an arbitrary container — supports fullscreen). Available to every participant, not just the host, since it only affects that viewer's own local display.
- **No way for the host to seek.** Rather than build a custom scrub bar, the `<video>` element's native `controls` are now enabled for the host only (toggled in `renderMembers`, alongside the existing `hostControls.hidden` toggle, so it follows host-transfer correctly). The existing `seeked` event listener (§5, native video event → host command forwarding) already forwards host seeks to the server — enabling native controls was the only piece missing. Left off for participants deliberately: their local seeking wouldn't propagate anywhere (only the host's commands reach the server), so exposing it would just be confusing UI for something the drift-correction loop would silently undo a second or two later — consistent with participants' play/pause controls already being hidden the same way.

### 5.6 §5.4's assumption was wrong: the offset has to be calibrated, not assumed

§5.4 flagged its own key assumption as unverified: that a transcode session Emby starts mid-item resets its HLS output's timeline to 0 (matching Emby/Jellyfin's documented behavior for a user-initiated seek), requiring the client to add the requested `StartTimeTicks` back to `video.currentTime` to recover the item's real position. Once deployed, a guest joining a party in progress landed consistently *behind* the host — by roughly the same offset that had just been added. That's the signature of the assumption running backwards: if this particular Emby build/config instead preserves the source's absolute timestamps in its HLS output (`video.currentTime` already close to the real item position), then adding the requested offset on top of it overshoots — no, *undershoots* the target by that same amount when converting back down via `videoSeconds`, landing every seek that many seconds early. Rather than swap the assumption for its opposite (equally a guess, just a different one — and Emby's actual behavior here isn't guaranteed to be consistent across versions/configs/transcode paths either), the client now **calibrates** the offset from observed reality instead of asserting it.

`video.seekable` reflects where a loaded stream's timeline *actually* starts, once the browser has enough of the manifest/segments to know — regardless of which convention Emby used to produce it. `calibratePlaybackOffset` reads `video.seekable.start(0)` once it's populated (checked on both `loadedmetadata` and `canplay`, since which one first has it populated isn't consistent across browsers/hls.js) and computes `playbackOffsetTicks = requestedStartPositionTicks - seekableStartTicks`: if Emby reset to 0, `seekableStartTicks` is ~0 and this reduces to the original assumption (add back the full requested offset); if Emby preserved absolute timestamps, `seekableStartTicks` is already close to `requestedStartPositionTicks` and the computed offset collapses to ~0 (no adjustment needed, matching direct play/stream's existing no-op case). Either way, the client converges on the correct offset from what's actually true of *this* stream, rather than a hardcoded belief about what Emby does in general. The moment calibration lands, the client immediately re-seeks to the currently-expected authoritative position using the corrected offset, since any seek attempted before calibration (using only the pre-calibration best guess) may have landed wrong — exactly the bug this section fixes.

This pattern generalizes past this one bug: anywhere this codebase was tempted to assert a third-party system's undocumented-for-this-version behavior instead of observing it, prefer observing it.

### 5.7 End party was hidden from participants in intent, but not in the UI

The end-party button (`#end-btn`) was never wrapped in the same host-only visibility toggle as the rest of the host controls (`#host-controls`) — participants saw and could click it, receiving a server-side `403` (`handleEndParty` correctly checks `p.HostUserID() != user.ID` — this was never an authorization gap, only a UI one). Fixed by giving it the same `hidden`-by-default treatment as `#host-controls`, toggled in `renderMembers` alongside it, so a participant now simply doesn't see a button that could only ever error out for them. `#leave-btn` deliberately stays unconditionally visible — unlike ending, leaving is something every participant, not just the host, can legitimately do.

### 5.8 §5.6's recalibration listeners weren't actually one-shot, and that mattered a lot

§5.6 added `loadedmetadata`/`canplay` listeners that recalibrate the playback offset and re-seek to the corrected position — reasoned through as "fires once near start, and firing again is a harmless no-op." The "harmless no-op" half was wrong in a way that only shows up under real playback conditions: `canplay` is not a fires-once event. It refires every time the media recovers from a stall (`HAVE_FUTURE_DATA` reached again after dropping below it) — which is a routine, expected event on real network video, especially when Emby's transcoder is itself the bottleneck (e.g. contending with another concurrent transcode session for the same hardware encoder) rather than the network. Every recovery re-triggered `recalibrateAndReseek`, forcing another programmatic seek — which itself interrupts playback and demands more data from Emby's transcoder right as it was already struggling to keep up, making the next stall both more likely and worse. The reported symptom was exactly this: choppy playback, and a native scrub bar that looked unresponsive because a background seek kept fighting whatever position the user's own interaction (or normal playback) had just reached.

Fixed with `{ once: true }` on both listeners, so `recalibrateAndReseek` runs at most once per event type — twice total in the worst case, across this page's entire session, not once per stall. The calibration itself doesn't need to run more than once anyway: `video.seekable`'s lower bound for a given transcode session doesn't change over the life of that session, only the upper bound (buffered-so-far) does.

A related fix landed alongside this: the "Start Playback" overlay sits directly over the video, including the native controls bar underneath it, whenever it's shown. Combined with the reseeking bug, a host who saw native controls appear (from §5.5) but tried clicking the native play button instead of the overlay's own button was clicking something the overlay was silently absorbing — `.overlay` is now `pointer-events: none` (only its button is `pointer-events: auto`), so a click anywhere else on the video reaches the native controls underneath, which is itself a valid trusted-gesture way to start playback, same as the overlay's own button.

### 5.9 §5.6's calibration signal couldn't see keyframe snapping

After §5.8 stopped the reseek loop, a guest joining a party in progress still landed consistently behind the host — smaller than the original error, but still tens of seconds, not the sub-second residual normal drift correction is meant to absorb. §5.6's calibration compared `video.seekable.start(0)` against `requestedStartPositionTicks` (what was asked for) to determine whether Emby had reset its output timeline to 0 or kept the source's absolute timestamps. That correctly resolves *that* question, but misses an entirely separate source of error: Emby can only start an HLS segment on a keyframe, so the actual start of a mid-item transcode session is silently snapped back to the nearest keyframe at or before whatever `StartTimeTicks` was requested — and a snapped-back start looks identical in `seekable.start(0)` under either timeline convention (still ~0 if reset, still ~"close to requested" if absolute), so nothing about that comparison could ever detect it.

The fix swaps the calibration signal entirely: compare `video.duration` (how much playable content this specific stream actually contains) against the item's real, known total duration (`itemDurationTicks`, already available from the party info `main()` fetches). The gap between them is exactly how much was skipped at the start — full stop, regardless of *how* it was skipped. This isn't a refinement of the reset-vs-absolute question, it's a different, strictly more direct measurement: a transcode session covering item range `[snappedStart, fullDuration]` reports `video.duration = fullDuration - snappedStart` no matter which convention `video.currentTime` itself follows, since duration is a span, not an absolute position. `calibratePlaybackOffset` (still gated behind the same `{ once: true }` `loadedmetadata`/`canplay` listeners from §5.8) now computes `playbackOffsetTicks = itemDurationTicks - videoDurationTicks` instead of comparing against the request at all.

### 5.10 Removed: the custom "Start Playback" overlay

Browsers refuse to autoplay unmuted video without a direct user gesture. Since server-driven playback (`applyAuthoritativeState` → `programmaticPlay`) is never itself a user gesture, the first attempt on any fresh page load is essentially always rejected — the overlay/button existed purely to give the user *something* to click that satisfies that requirement, entirely separate from the server-side "is the party playing" state (clicking it never sent anything to the server; it only unblocked this browser's own ability to call `.play()`).

Across §5.5, §5.8, and reports after both, this custom mechanism repeatedly ended up desynced from reality — shown over already-playing video, or blocking clicks meant for the native controls sitting right underneath it. §5.5 had already added real native `<video controls>` for the host, which includes the browser's own play button — and clicking a browser's own native control is unconditionally treated as a valid gesture by that same browser, with no custom code involved to get wrong. Native controls are now enabled unconditionally, for every participant, not just the host (`<video controls>` directly in `party.html` rather than a per-render `isHost()` toggle), and the overlay is gone entirely — `programmaticPlay`'s autoplay-blocked case now does nothing but reset its own `suppress` flag, since the always-visible native play button is the affordance.

This does give every participant, not just the host, a native seek bar and play/pause buttons — previously host-only, on the reasoning that a participant's local seeking "wouldn't do anything but confuse them." That reasoning still holds in the sense that it's harmless: only the host's play/pause/seek interactions are ever forwarded to the server (the existing `isHost()` gate in the native-event listeners, unchanged), so a participant's own scrubbing only affects their own local view and gets silently corrected back by the drift loop, same as any other drift. It trades a small amount of tidiness (a participant *can* fiddle with controls that don't stick) for removing an entire class of bugs a custom parallel mechanism kept reintroducing.

## 6. Container privilege model: PUID/PGID without a shell

**The decision to make.** Self-hosted users commonly expect a `PUID`/`PGID` pair (the linuxserver.io convention) so the container writes files as a UID/GID that matches whatever owns a bind-mounted host directory, rather than some arbitrary container-internal ID the host user can't read or clean up. The image was originally built on `gcr.io/distroless/static-debian12:nonroot` (see the original Dockerfile), which hardcodes UID/GID 65532 with no shell to change it at runtime — the classic way other images support `PUID`/`PGID` (start as root, `chown` the volume, then `su-exec`/`gosu` down to the target user before exec'ing the real process) is unavailable, since that whole pattern depends on a shell and a small setuid helper binary, and distroless deliberately has neither.

**Alternatives considered:**
- **Switch the final stage to a minimal shell-having base (e.g. Alpine) with a `su-exec`-based entrypoint script.** This is the standard, well-trodden approach, but it gives up the "no shell, no package manager, minimal attack surface" property that was a deliberate earlier choice (§ Dockerfile comments) — trading a meaningful chunk of the image's reduced attack surface for a feature that a few dozen lines of Go can provide instead.
- **Drop privileges in-process in the Go binary itself, no shell required.** Chosen. The server, while still root, `chown`s its data directory to `PUID:PGID` and then permanently drops privileges to that UID/GID before opening the database or listening on anything — implemented in `internal/privdrop`.

**The part that's easy to get wrong.** A naive privilege drop in Go — a single `syscall.Setuid`/`syscall.Setgid` call — only changes credentials for the *calling OS thread*. The Go runtime spreads a process across multiple OS threads from the moment it starts, so a naive drop can leave other threads (and thus, eventually, other goroutines) still running as root, which is a real, documented Go pitfall, not a hypothetical one. `internal/privdrop` uses `syscall.AllThreadsSyscall` (added in Go 1.16 specifically for this class of problem) to apply `setgroups(0)` → `setgid` → `setuid` atomically across every OS thread. This requires `CGO_ENABLED=0`: `AllThreadsSyscall`'s own documentation states it "always returns ENOTSUP in binaries that use cgo," since it can't see threads created by cgo-linked code — which this project already builds with regardless, since `modernc.org/sqlite` is a pure-Go driver (§1.2). `internal/privdrop`'s tests exercise the real syscalls (in a re-exec'd subprocess, so the drop's irreversibility can't affect the test runner itself) rather than mocking the mechanism, specifically because this is the kind of code where a plausible-looking mock would hide exactly the bug that matters.

**Default.** `PUID`/`PGID` default to `65532` each when unset — the same UID the image used to hardcode via the `:nonroot` tag — so upgrading without setting either variable preserves existing file ownership and keeps the "secure by default, no configuration required" property. If the resolved UID or GID is `0`, the server logs a warning and continues (an operator may have a legitimate niche reason to want this) rather than refusing to start, since silently overriding an explicit operator choice would be its own kind of surprising behavior.

## 7. Frontend redesign: dashboard + party UI

The original frontend (§1.6-era) was deliberately minimal — plain forms, no styling investment — while the sync engine and Emby integration were the actual hard problems worth spending effort on. Once those were working end-to-end (§5's postmortems), a real visual design pass followed a supplied mockup: a dark, sidebar-navigated dashboard (login → home → party), built with Space Grotesk/Inter/JetBrains Mono.

**Fonts are vendored, not CDN-loaded** (`web/static/fonts/`, see its `README.md`) — same reasoning as hls.js (§1.6): a self-hosted app shouldn't need internet access to render its own UI. Each family ships as a single variable-weight WOFF2 covering the `latin` subset only; Google's own CSS2 API serves the *same file* for every weight of a family it was asked for (the weight comes from `font-variation-settings`, not a separate file per weight), so there's genuinely one file per family to vendor, not one per weight. This is also why static assets being cacheable matters more now than it did (§1.7) — the font files alone are worth not re-fetching every request, while still needing to roll over cleanly on the next redesign.

**The mockup includes features this pass didn't build**: a chat panel, and browsable Parties/History/Settings destinations beyond Home. Rather than omit them (which would make the shipped UI look unfinished/broken relative to the design) or fake them (which would mislead), these render with their real visual chrome but inert and visibly marked — a `.coming-soon-badge` pill and `.is-coming-soon` (50% opacity, `pointer-events: none`) on the containing element. This is a deliberate, reusable pattern for "designed but not yet built," distinct from simply hiding a section.

**Two mockup sections *were* built for real rather than stubbed** — Active Parties and Your Parties — because the gap turned out smaller than it looked: `party.Hub.All()` and `Party.Snapshot()`/`CurrentPositionTicks()` already exposed everything needed except a title, and `handleGetParty` was already calling `Emby.GetItem` per party (for its access-check) — reusing that call for a title cost nothing extra. The new `GET /api/parties` (`handleListParties`) iterates every party the in-memory `Hub` currently holds and resolves each one's title via the *requesting user's own* Emby token, per this codebase's hard rule that no shared/service token is ever used for a specific user's view of anything (§0.2). A party whose item that specific user can't see (or that Emby can't otherwise resolve) is silently omitted from their listing rather than failing the whole request — matching the same access-control spirit as `handleGetParty`'s join-time check, just applied per-row instead of per-request. There's no per-party visibility list beyond that: every active party is visible to every signed-in user, consistent with this being a small friends/family tool (join-by-link already implied this) rather than a multi-tenant service.

**The party page's video element keeps native `<video controls>`** rather than the mockup's fully custom scrub bar/transport buttons — enabled unconditionally now (§5.10), not merely styled to match. This was an explicit tradeoff made with the user rather than a default: native controls have already replaced a custom playback-gesture mechanism once (§5.5, §5.8, §5.10) specifically because the custom version kept ending up desynced from reality, and rebuilding an equivalent custom transport bar now would reintroduce the same category of risk for a purely cosmetic gain.

**Create Party uses a native `<dialog>` element**, not the mockup's single-button-only home page — the mockup doesn't show an item-ID input at all, implying a full Emby-library-browsing picker that doesn't exist yet. Rather than build that now or leave the existing manual-ID flow looking out of place bolted onto the header, it moved behind a button that opens a modal (`showModal()`/`.close()`, no library dependency needed for a native element with broad support), keeping the dashboard's visual hierarchy close to the mockup while preserving the existing required input. A separate "Join by link" dialog existed briefly alongside it (for pasting a party URL/ID directly) but was removed once Active Parties made it redundant for the normal case — joining via a directly-pasted `/party/{id}` URL still works fine, it's just no longer a distinct dashboard affordance.

**Ending a party now navigates back to Home**, matching Leave (both are terminal for the current viewer — there's nothing left on the party page to show once it's over).

**The sidebar and main content are two independently scrollable panes**, not one page that scrolls as a whole. `.app-shell` is pinned to `height: 100vh` (not `min-height`, which is what let the whole page grow past the viewport in the first place); `.sidebar` and `.main-content` each get `min-height: 0` (overriding a flex item's default `min-height: auto`, which otherwise forces the row taller than its container to fit content instead of letting the item scroll) plus their own `overflow-y: auto`. A tall dashboard now scrolls its own content while the sidebar stays put, and a sidebar with more nav items than fit scrolls independently too — without ever producing a second, redundant scrollbar on `<body>`, since `.app-shell` never actually grows past `100vh` for `<body>` to scroll in the first place.

## 8. Party self-destruct: ending an abandoned party automatically

**The decision to make.** A party has no owner-initiated cleanup beyond the host explicitly clicking "End party" — if everyone just closes their tabs (or the host's browser/device dies) without doing that, the party stays `active` in the database and in the `Hub` forever, its actor goroutine idling, its row never leaving the `Active Parties` listing. For a self-hosted tool with no admin UI for manually cleaning this up, that's a real, if slow-motion, leak — worth an automatic timeout rather than requiring an operator to notice and intervene.

**What counts as "activity."** Two independent signals, whichever is more recent: a play/pause/seek control (`playback_state.server_timestamp`, already persisted for the sync protocol itself) and any member connecting or reconnecting (`party_members.last_connected_at`, already persisted for member-list display). Either alone can keep a party alive — a party nobody's touched the transport controls on for two days but someone reconnected to an hour ago is clearly not abandoned, and vice versa. Falling back to the party's `created_at` covers the edge case of a party created and then immediately walked away from, with neither signal ever having fired. Deliberately *not* used as a signal: mere passage of time while `IsPlaying` is true with no seek/pause — the item's own duration and `checkEndOfMedia`'s existing detection already bound how long that can plausibly go on for a normal-length video.

**Why no new database column.** Both signals above were already being persisted for unrelated reasons (sync protocol state, member-list UI) — `Hub.lastActivityAt` just reads them back and takes the max, rather than introducing a dedicated `last_activity_at` tracked separately. This also makes the mechanism restart-safe for free: since it's computed from already-persisted, already-recovered data rather than an in-memory-only timer, a container restart can't accidentally reset an already-nearly-stale party's clock back to zero.

**Where the sweep runs.** `Hub.SweepInactiveParties(ctx, maxIdle)` iterates every party the `Hub` currently holds, computes each one's last activity, and calls the existing `Hub.EndParty` (the same path a host's own "End party" click goes through — no separate/parallel termination logic to keep in sync) for anything past `maxIdle`. `cmd/server/main.go` runs this on a plain `time.Ticker` loop (`partyInactivitySweepInterval`, 15 minutes — deliberately not itself configurable, since 15 minutes of imprecision against a multi-hour timeout is immaterial) alongside the existing per-user Emby-progress-reporting loop, both stopped via the same shutdown-context pattern. `PARTY_INACTIVITY_TIMEOUT` (default `48h`) is the operator-configurable threshold.

## 9. Playlist-based parties

**The decision to make.** The original design locked a party to exactly one Emby item, chosen at creation and fixed for the party's whole lifetime (`parties.item_id`/`duration_ticks`, immutable fields on the party actor). The requested change — create a party by name only, add media afterward through a browsable playlist, advance automatically at end-of-media — touches three of this project's hard invariants at once: server-authoritative playback state (an item change is itself an authoritative state transition, not a side detail), per-participant Emby re-authorization (written under "one fixed item," which a playlist breaks), and "no shared token, ever" (a new library-browsing surface needs its own answer to who's making Emby calls with what token). Five things were decided; each is covered below.

### 9.1 End-of-media → playlist advance, reusing the existing actor/sequence machinery

`party.Party` used to expose `ItemID`/`DurationTicks` as fields set once in `newParty` and never touched again. They're gone; in their place, the actor carries **do()-serialized mutable state** exactly like `state State` already was — a `current *currentItem` (nil means idle: nothing loaded) and a `playlist []dbx.PlaylistItem` cache (loaded at construction/recovery, mutated by the new playlist actor methods, mirrored to `playlist_items`).

`checkEndOfMedia` used to do `state = {PositionTicks: DurationTicks, IsPlaying: false, ...}` and broadcast a `pause`. It now looks up `nextPlaylistItemAfter(current.PlaylistItemID)`:
- **Found** → advance: new `current`, `state = {0, true, seq+1, now, nil, system}`. Deliberately auto-continues playing rather than requiring the host to press play again per item — a playlist is a queue that plays through, and this is still entirely server-decided (`ClientTypeSystem`), consistent with "the host client's `ended` event is an observation, not an authoritative command."
- **Not found (queue exhausted)** → idle: `current = nil`, `state = {0, false, seq+1, now, nil, system}`. No new "ended" status was needed: idle is already the state a freshly-created, empty-playlist party starts in under the new create flow, so end-of-playlist just returns to it.

Both paths go through one new helper, `transitionCurrent(next *currentItem, playing bool, byUserID *string, clientType dbx.ClientType)`, shared with the host-explicit case (`SelectCurrentItem`, §9.3) — one code path for every way the current item can change, not three. It broadcasts a full `snapshot` (not `broadcastControl`) since `ItemID`/`DurationTicks` only live on `SnapshotPayload`, and — critically — bumps the *same* `state.SequenceNumber` counter every other authoritative change uses. This was the one design question worth pausing on: does an item transition need its own numbering/staleness scheme? No — because it's still just another mutation of `p.state`, the existing client-side `IsStale` rejection (delayed message with an older sequence number is dropped) already protects a delayed pre-transition snapshot from clobbering a newer item transition, for free.

**Removing the currently-playing item is rejected outright** (`ErrCannotRemoveCurrentItem`), not implicitly resolved by auto-advancing or going idle — the host must explicitly choose what happens next. A smaller, more predictable surface than guessing what the host wanted.

### 9.2 Media re-authorization: the check already lives at the right place, it just needed to fire more often

The old join-time check (`handleGetParty`/`handleWebSocket` calling `Emby.GetItem` against the party's one fixed item) assumed there was nothing to re-check later. With a playlist, the current item changes after join — but the natural re-validation point already existed and needed zero new authorization code: **`handlePlaybackURL`**, which every client already calls, per-user, with that user's own token, any time it needs a stream URL — on join, on reconnect, and now on every item transition too, since a new item always needs a new URL. `Emby.GetPlaybackURL` → `PlaybackInfo` already rejects an item a user can't see; that rejection now surfaces per participant, per item, exactly at the moment it matters, with no party-wide side effect — one participant being denied item B doesn't touch anyone else still watching it.

The join-time gate didn't disappear — `handleGetParty`/`handleWebSocket` still run it — but it's now conditional on `snap.ItemID != ""`. An idle party (nothing loaded, true of every party immediately after creation now) has nothing to authorize against yet; the check simply resumes mattering once there is a current item.

**Playlist metadata is a smaller privacy question, decided the same way `handleListParties` already decided it.** `GET /api/parties/{id}/playlist` resolves each item's title/poster using the *requesting viewer's own token*. An item that viewer can't access is shown as a generic "Restricted item" placeholder rather than its real title (a metadata leak about content they're not authorized to know exists) or silently omitted (an unexplained gap in the queue's order).

### 9.3 Playlist mutation authorization: host-only

Presented to the operator as a real decision (add-only-by-anyone and fully-open alternatives were both on the table) rather than assumed. **Decided: host-only**, for add/remove/reorder alike, plus `SelectCurrentItem` ("play this now") as an extension of existing play-authority. This adds zero new authorization concepts — `AddPlaylistItems`/`RemovePlaylistItem`/`ReorderPlaylist`/`SelectCurrentItem` are gated exactly like `HandleControl`/`HandleHostTransfer` already were (`ErrNotHost` if `userID != p.hostUserID`), rather than introducing a "participant may mutate shared state" tier that doesn't exist anywhere else in this codebase. The HTTP handler for adding items checks host status *before* decrypting a token or calling Emby (`handleBatchAddPlaylistItems`), not just inside the actor — a non-host's request shouldn't cost a round trip it's going to be rejected regardless of.

Unlike `HandleControl`/`HandleHostTransfer`, `AddPlaylistItems`/`RemovePlaylistItem`/`ReorderPlaylist` need a SQLite write to complete (to hand back assigned ids/positions, or to prevent an in-memory cache update from outrunning a write that ends up failing) — but the codebase's rule that party-state mutation never blocks on synchronous IO still applies just as much to an occasional playlist edit as it does to the hot play/pause/seek path. Each of these methods dispatches through the actor **twice**: once (fast, IO-free) to authorize, then the SQLite write happens in the calling goroutine outside `do()`, then a second fast dispatch applies the result to `p.playlist` and broadcasts. This leaves a small, harmless window where the party could end or the host could change between the two dispatches — the same order of imprecision this codebase already accepts around `CurrentPositionTicks` — in exchange for never letting a disk write stall sync broadcasts for everyone else in the party.

### 9.4 The library browser: backend endpoint, not direct-to-Emby — a deliberate departure from the playback-URL pattern

The existing design has exactly one case where the browser talks to Emby directly: the constructed media stream URL, for two specific reasons (§0.2, §5) — a `<video src>`/hls.js request can't set custom headers (forcing query-param `api_key` auth), and proxying media *bytes* would mean reimplementing Range/HLS-manifest passthrough, precisely the complexity the "no proxy" invariant exists to avoid.

**Neither reason applies to a JSON search/browse call.** A `fetch()` can set headers freely; item metadata responses are tiny. So `GET /api/emby/items` goes through the Go backend, using the requester's own decrypted token — the same shape as `GetItem`/`PlaybackInfo`/`Sessions/Playing*`, all of which already go through the backend. The library browser is architecturally closer to `GetItem` than to the stream URL; treating it like the stream URL would only widen the one CORS surface this project has already spent five bug-fix rounds getting right (§5.1–§5.9) for no benefit, and would duplicate Emby API knowledge (pagination, filter mapping) into vanilla JS with no build step, which §1.6 already declined to do for anything beyond ~150 lines of stable sync math.

**Poster images are the deliberate exception, and they follow the stream-URL pattern on purpose.** An `<img src>` has the same "no custom headers" constraint a `<video src>` does, and a thumbnail JPEG isn't what the "no proxy" invariant is protecting (that invariant is about streaming/Range/transcoding, not a few KB of poster art). So `GET /api/emby/items` returns a ready-to-use, `api_key`-bearing poster URL per item (`emby.Client.ImageURL`, built the same way `GetPlaybackURL` builds a stream URL, via `publicBaseURL`), and `<img>` tags hit Emby directly for the bytes — consistent with the existing design, not a deviation from it.

`emby.ItemsQuery`/`ListItems` cover the four browser tabs (`IncludeItemTypes=Movie`/`Series`, `SortBy=DateCreated&SortOrder=Descending` for Recently Added, `Filters=IsFavorite` for Favorites) plus free-text search (`SearchTerm`). Endpoint shape is new, unverified-against-a-live-server research, in the same spirit as the rest of `internal/emby` (§0) — treat it accordingly until confirmed.

§9.7 extends this same backend-routed pattern to series→season→episode drill-down (`ListSeasons`/`ListEpisodes`) and to the batch-add path's bulk item lookup (`GetItems`) — none of these are a new architectural decision, just more calls following the shape this section already established.

### 9.5 Schema

```sql
CREATE TABLE playlist_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    party_id TEXT NOT NULL REFERENCES parties(id) ON DELETE CASCADE,
    item_id TEXT NOT NULL,              -- Emby ItemId
    duration_ticks INTEGER NOT NULL,    -- fetched from Emby at add-time, authoritative
    position INTEGER NOT NULL,          -- 0-based order within the party's queue
    added_by_user_id TEXT NOT NULL REFERENCES users(id),
    added_at TEXT NOT NULL
);
CREATE UNIQUE INDEX idx_playlist_items_party_position ON playlist_items(party_id, position);

ALTER TABLE parties ADD COLUMN name TEXT NOT NULL DEFAULT '';
ALTER TABLE parties ADD COLUMN current_playlist_item_id INTEGER REFERENCES playlist_items(id) ON DELETE SET NULL;
ALTER TABLE parties DROP COLUMN item_id;
ALTER TABLE parties DROP COLUMN duration_ticks;
```

`parties.item_id`/`duration_ticks` are dropped outright, not left vestigial — "current item" lives solely as `current_playlist_item_id` pointing into `playlist_items` (which also carries that item's own `duration_ticks`, fetched once at add-time), so there's exactly one source of truth instead of two that could drift apart. `playlist_items.id` is a plain autoincrement integer, not a crypto-random ID like party/session IDs: it's never used unguessably on its own (always scoped under `/api/parties/{partyID}/playlist/{id}`, which already requires party membership to reach), so the extra randomness `idgen` provides elsewhere buys nothing here. `ReorderPlaylistItems` writes new positions through a temporary negative range first (`UPDATE ... SET position = -(i+1)`, then `= i`) rather than directly — `idx_playlist_items_party_position`'s unique index isn't deferrable in SQLite, so writing final positions one row at a time would collide with whatever row currently holds the destination position on anything but an append (a plain two-item swap is enough to trigger it).

**Wire protocol.** A new `wsproto.MsgPlaylistUpdated` message is broadcast on add/remove/reorder (current-item changes already go through the existing `snapshot` broadcast, which already carries `ItemID`/`DurationTicks`). Its payload is deliberately just the raw ordered `{id, item_id, position}` rows — the party actor has no Emby access, by design, so it can't resolve titles itself. Clients treat it as an invalidation signal and re-`GET /api/parties/{id}/playlist`, which resolves human-facing metadata under the *viewer's own* token (§9.2) — simpler than diffing/optimizing client-side, and appropriate at this project's scale.

### 9.6 Frontend

`player.js` used to fetch a playback URL exactly once, at page load, on the assumption that the item never changes. It now tracks `currentItemId` and re-fetches (`loadCurrentItem`) whenever a snapshot's `item_id` differs from what's currently loaded — including the idle case (`item_id === ""`), which shows a placeholder over the video element rather than leaving a frozen or empty `<video>`. One consequence worth flagging: `recalibrateAndReseek`'s `{ once: true }` `loadedmetadata`/`canplay` listeners (§5.8 — deliberately one-shot, since `canplay` refires on every stall recovery and re-arming per stall caused a real reseek-loop bug) have to be re-armed on every new item load now, not registered once at module scope — `attachSource` re-registers them each call, since each new item's stream needs its own calibration pass.

A new `playlist.js` module owns the Playlist section (list rendering, host-only play/remove buttons, and a host-only drag handle for reordering) and its "Add to playlist" browse dialog (search box, Movies/TV Shows/Recently Added/Favorites tabs, poster grid pulled from `GET /api/emby/items`), imported by `player.js` the same way `ws-client.js`/`sync.js` already are. §9.7 extends this dialog with drill-down and multi-select; its selection-state logic lives in a separate pure module, `playlist-select.js`, following the same split §1.6 already established for `sync.js`.

**Drag-and-drop reordering** is single-item only (no multi-select drag) and wired to the reorder endpoint §9.3 already established (`PUT /api/parties/{id}/playlist/order` → `ReorderPlaylist`) — no new backend surface. Each row gets a drag handle, gated `handle.hidden = !isHostFn()` the same way every other host-only control in this UI is (§11.5). Unlike the play/remove buttons, which are hidden for the currently-playing row, the handle stays live for it too: only *removing* the current item is rejected (`ErrCannotRemoveCurrentItem`); `ReorderPlaylist` has no such check and only rejects a mismatched id set, so moving the current item's position is intentionally allowed. The reorder math (`reorderIds` in `playlist-select.js`) is a pure function, unit-tested the same way the rest of that module is — given the currently-rendered id order, the dragged id, and the drop target's id/before-or-after, it returns the new order, which `playlist.js` then PUTs and reloads the list from. Implemented with the native HTML5 Drag and Drop API (`draggable` + `dragstart`/`dragover`/`drop`) rather than a library, consistent with this frontend having no bundler or dependencies (§1.6) — `dragstart` calls `dataTransfer.setData()` defensively (Firefox requires it to initiate a drag at all) even though the drop handler reads the dragged id from a module-scoped variable instead, since `dataTransfer.getData()` isn't reliably readable outside the `drop` event in every browser. **Known limitation, deliberate:** native HTML5 drag-and-drop has no touch/mobile equivalent — there's no way to drag-reorder from a phone or tablet with this API, so this feature is effectively desktop/mouse-only for now, the same trade-off this project accepts elsewhere rather than pulling in a pointer-events-based DnD library for one control.

### 9.7 Season/episode selection: drill-down, recursive multi-select, and one atomic batch-add

The playlist browser above only ever added a whole movie or a whole series as a single row — there was no way to queue an individual episode, a season, or a hand-picked set of episodes. Three backend additions and one frontend restructure close that gap, all as extensions of decisions already made in this section rather than new ones.

**Browsing.** `emby.Client.ListSeasons`/`ListEpisodes` (`GET /Shows/{seriesID}/Seasons`, `GET /Shows/{seriesID}/Episodes?seasonId=...`) and their handlers `handleListSeasons`/`handleListEpisodes` (`GET /api/emby/series/{id}/seasons`, `GET /api/emby/seasons/{id}/episodes`) are a direct extension of §9.4's backend-routed pattern — requester's own token, JSON metadata through this backend, not host-gated (browsing was already open to any authenticated member, same as `handleBrowseEmbyItems`). `ListEpisodes` requires `seriesID` alongside `seasonID` because Emby's episode listing is scoped under the series rather than the season; the frontend already has it (`SeasonSummary.SeriesID`) from whichever call produced the season being drilled into, so this never costs an extra round trip. Like `ListItems` before it, both endpoint shapes are unconfirmed against a live Emby server — same caveat as §9.4's closing paragraph, not extended any further confidence here.

**`EpisodeSummary.RunTimeTicks` comes straight from the episode-listing response**, never a follow-up per-episode call — Emby's episode listing already includes it per item. Fetching it separately would turn "select a 20-episode season" into 21 Emby round trips purely to learn durations the first call already returned.

**Batch add: one endpoint, one transaction, one broadcast — not N calls to a single-item endpoint.** `POST /api/parties/{id}/playlist/batch` (`handleBatchAddPlaylistItems` → `Party.AddPlaylistItems` → `Store.AddPlaylistItems`) takes an ordered list of Emby ItemIds and adds them all in one pass: one host check, one Emby round trip, one SQL transaction (`Store.AddPlaylistItems` wraps every insert in a single `*sql.Tx`, positions assigned sequentially from the current max — same technique `ReorderPlaylistItems` already uses for a multi-row write), one `p.do()` dispatch appending to `p.playlist` and calling `broadcastPlaylistUpdated` once. Doing this via N calls to the pre-existing single-item endpoint would have meant N authorize dispatches, N independent `SELECT MAX(position)+1` inserts (correct only by luck of sequential execution), and N broadcasts — a 30-episode season selection would visibly stream into the list item-by-item, and a mid-batch failure (host demoted, one item's access revoked) would leave a partially-added, inconsistent queue with no rollback. The old single-item HTTP endpoint (`handleAddPlaylistItem`, `POST /api/parties/{id}/playlist`) was removed rather than kept alongside the batch one: once the browse dialog's checkbox → batch-add flow replaced its click-to-add card handler, it had no remaining production caller, and an unused, separately host-checked mutation endpoint is exactly the kind of surface not worth carrying forward. (`Party.AddPlaylistItem`/`Store.AddPlaylistItem`, the underlying single-item Go methods, stay — they're still exercised directly by a large share of this codebase's existing test setup, unrelated to the HTTP layer.)

**The batch's Emby lookup is one call, not N, for the same reason the add itself is.** `emby.Client.GetItems(ctx, token, userID, itemIDs)` — `GET /Users/{userId}/Items?Ids=id1,id2,...` — resolves every item's title/duration/access-check at once, a direct extension of `ListItems`'s already-in-use `Users/{userId}/Items` call (just adding the `Ids` filter), so lower-risk than `ListSeasons`/`ListEpisodes` but still unconfirmed against a live server for that filter specifically. Access enforcement carries over unchanged: the call is scoped to the requester's own token/userID, so an item that user can't see (or that doesn't exist) simply isn't in the response, exactly like `ListItems`/`GetItem` already behave. **That absence is what "no partial add" is built on**: `handleBatchAddPlaylistItems` diffs the requested id list against what came back, and any gap rejects the whole batch before a single row is written — the same effective behavior the old single-item endpoint got by erroring on the first inaccessible item, just detected by a set difference instead of a failed call, and now covering the whole batch atomically instead of stopping partway through a sequence.

**Confirmation for large recursive selections is a real `<dialog>`, not `window.confirm()`.** Checking a series or season checkbox that would newly select ≥25 episodes (`LARGE_SELECTION_THRESHOLD` in `playlist-select.js`) opens `#confirm-large-selection-dialog` — styled with this app's existing dialog/button CSS (same family as `create-party-dialog`/`browse-dialog`), which a native `confirm()` would have broken visual consistency with for no benefit. The threshold applies once per checkbox action (not per party of a fetch), and only to *checking* — unchecking, and the final "Add N Selected Item(s)" button, are never gated, since the risk this guards against is silently queuing a pile of items, not removing them.

**Recursive selection needs a fetch even without drill-down.** Checking a series/season checkbox has to know that node's full episode set to select it — whether or not the user ever navigated into it — so `playlist.js` maintains `seasonsCache`/`episodesCache` (keyed by series/season id) populated by either drill-down navigation or a checkbox's own on-demand fetch, whichever happens first, with a loading state on the checkbox while that resolves. Indeterminate state (some but not all descendants selected) is re-derived from these same caches after every selection-map mutation — it's `null` (rendered as unchecked) for a node whose children were never fetched, which is always correct: an episode can only ever enter the selection map after its season's episodes have been fetched, so nothing under an unfetched node can be selected.

**Selected Media panel order — and therefore batch-add order — is fully specified, not just "season/episode order."** The panel groups movies first (alphabetical by title), then TV (`[seriesName, seasonIndex, episodeIndex]`) — mirroring the browse dialog's own Movies-before-TV-Shows tab order rather than an arbitrary tiebreak, and deliberately never interleaving a movie title against a series name by alphabetical position. This lives as a pure function (`sortSelection` in `playlist-select.js`) over the selection `Map`'s values, which is also exactly what gets serialized into the batch request's `item_ids` — the panel's displayed order *is* the resulting playlist order, by construction rather than by convention.

**Schema: no migration.** `playlist_items.item_id` already stores an opaque Emby ItemId (§9.5); nothing there distinguishes a movie id from an episode id, and nothing needs to — `handleGetPlaylist` already resolves title/poster per row via `Emby.GetItem`, which works identically for either type.

## 10. Party Settings: the end-of-media countdown

**The decision to make.** §9 made end-of-media advance straight to the next playlist item. A follow-up request added four host-configurable settings around that: whether it auto-advances at all (`auto_advance`), whether a "next item in…" dialog is shown (`show_next_dialog`), whether the next item autoplays or just loads paused (`autoplay_enabled`), and how long to wait first (`autoplay_delay_seconds`). The one real design question — not "what are the settings" but "how does a multi-second countdown, visible to every participant, stay correct" — is covered here; everything else follows the same host-only, actor-owned patterns §9 already established.

**Server-authoritative, like everything else.** Independent per-client JS timers would drift relative to each other and could race to trigger the transition themselves — exactly the failure mode the whole sync engine exists to avoid. So the countdown is actor state, communicated the same way every other authoritative change already is: no new message type, just more fields folded into the existing `snapshot`/`sequence_number` broadcast (`wsproto.SnapshotPayload` gained `PendingTransition *PendingTransition` — `{deadline, autoplay}`, an absolute RFC3339Nano timestamp, not a relative "seconds left" — plus the four settings fields themselves, `AutoAdvance`/`ShowNextDialog`/`AutoplayEnabled`/`AutoplayDelaySeconds`, and `Name`, promoted from an HTTP-response-only field to the snapshot proper so a host rename now propagates live to everyone connected instead of only the next page load). Because `buildSnapshot()` already assembles every field fresh from live actor state on every call, a client joining or reconnecting mid-countdown gets the exact same absolute deadline as everyone else, automatically — there is no separate "resume the countdown for latecomers" code path to get wrong.

**`checkEndOfMedia` (party.go) branches on settings, not just on whether a next item exists:**
```go
if !p.settings.AutoAdvance || p.nextPlaylistItemAfter(p.current.PlaylistItemID) == nil {
    p.transitionCurrent(nil, false, nil, dbx.ClientTypeSystem) // idle, immediately
    return
}
p.enterPendingTransition()
```
`auto_advance: false` always goes idle immediately, even when a next item genuinely is queued — the setting's confirmed meaning is "don't auto-advance," full stop, not "advance but skip the countdown." Reaching the end with nothing queued also skips straight to idle rather than counting down to nothing.

**Entering the countdown clamps state, it doesn't leave it stale.** `enterPendingTransition` sets `p.state` to paused-at-duration (exactly what the pre-Party-Settings end-of-media pause already did) before starting the timer, rather than leaving `IsPlaying: true` for the length of the countdown. This isn't cosmetic: `CurrentPositionTicks()` extrapolates forward from `p.state` while `IsPlaying` is true, so an unclamped state would keep climbing past the item's real duration for as long as the countdown ran — and `handlePlaybackURL` hands that number to Emby as `StartTimeTicks` for anyone who (re)joins mid-countdown, i.e. a real bug, not a theoretical one, caught by reasoning through the existing `CurrentPositionTicks` contract rather than by observation. Clamping also means embyreport's next periodic tick correctly reports `IsPaused: true` at the true final position with no special-casing on its end.

**"What's next" is resolved at the deadline, not when the countdown starts.** `pendingTransition` deliberately carries only `{Deadline, Autoplay}` — no item reference. `onPendingTransitionFired` calls `nextPlaylistItemAfter` fresh when the timer actually fires:
```go
func (p *Party) onPendingTransitionFired() {
    pending := p.pending
    p.pending, p.pendingTimer = nil, nil
    next := p.nextPlaylistItemAfter(p.current.PlaylistItemID)
    if next == nil {
        p.transitionCurrent(nil, false, nil, dbx.ClientTypeSystem)
        return
    }
    p.transitionCurrent(&currentItem{...}, pending.Autoplay, nil, dbx.ClientTypeSystem)
}
```
The alternative — capture "next" when the countdown starts — would need its own invalidation story for every playlist edit that could happen during those few seconds (an item removed, reordered, or added ahead of it). Resolving fresh sidesteps all of that: a host editing the queue mid-countdown just works, and `RemovePlaylistItem` needs no new guard for "is this the pending target" the way it already guards the *current* item. The cost is that the dialog can't name the upcoming title — acceptable, since the confirmed dialog text ("Next item in…" / "Playback pauses in…") never names an item to begin with.

**Cancellation.** `transitionCurrent` clears any pending transition unconditionally at its start — covers a host explicitly picking a different item mid-countdown (`SelectCurrentItem`), and makes `onPendingTransitionFired`'s own call into it a harmless no-op re-clear. `HandleControl` (play/pause/seek) does the same at its start: a host command during the countdown is a manual-control signal (most commonly, replaying or seeking within the item that just ended) and cancels it. Because `pending_transition` only lives on the full `SnapshotPayload` shape, not the narrower `AuthoritativeState` shape `broadcastControl` normally sends, a `HandleControl` call that had to cancel a pending transition broadcasts a full snapshot instead — the only place this distinction matters. `End()` cancels any pending transition too, so `onPendingTransitionFired` can never fire against an already-ended party (`run()`'s select loop rebuilds its timer channel as nil from `p.pendingTimer` on every iteration, so clearing it inside `End()`'s `do()` dispatch permanently disables that case on every later iteration — no separate `p.ended` check needed inside the handler itself).

**Timer mechanics.** `Party.run()`'s `select` loop gains a case sourced from a nil-able channel, rebuilt from `p.pendingTimer` every iteration — the standard Go idiom for a cancelable one-shot timer inside a `select` (a nil channel simply never becomes ready, so the case just doesn't fire until a real timer is installed). A dedicated `time.Timer`, not the existing `snapshotTicker`, is what's needed here: `autoplay_delay_seconds` can be shorter than the snapshot broadcast interval, so piggybacking on that ticker would make short countdowns visibly late.

**Not persisted across a restart.** `p.pending`/`p.pendingTimer` are in-memory-only actor fields, like `hostDisconnectedAt` already was. Because `enterPendingTransition` already clamps and persists `p.state` to paused-at-duration, a restart mid-countdown recovers cleanly into "paused at the end of the last item" — `checkEndOfMedia`'s `!p.state.IsPlaying` guard means it won't spontaneously re-fire, so a host has to act (replay, or pick something from the playlist) to move on. Reconstructing a partial countdown's remaining time across a restart would be meaningfully more machinery for a rare edge case with a perfectly reasonable fallback already available.

**Authorization and settings mutation.** `Party.UpdateSettings(ctx, userID, name string, settings Settings)` is host-only, gated by the same `checkHostAuthorized` helper §9.3's playlist mutations use, and follows the identical two-phase pattern: authorize (fast, IO-free), write to SQLite outside `do()`, then apply-and-broadcast inside a second `do()` — never blocking the actor goroutine on disk IO. It broadcasts a full snapshot on success so already-connected participants see a host's rename or settings change immediately, not just on their next reconnect.

**Frontend.** `settingsForm.js` is a small shared module (imported by both `app.js` and `player.js`, which are otherwise two fully independent page entry points with no component system between them) wiring the four fields' interdependence — `show_next_dialog` and the autoplay controls disable whenever `auto_advance` is off, and the delay input additionally disables whenever "Auto-play after" itself is unchecked — plus `read()`/`write()` helpers so the create-party dialog and the party page's post-creation settings dialog (opened via a new cog button in the topbar, host-only visible) share one implementation of the field logic instead of two. `player.js` renders the countdown as a small pill-shaped banner overlaid on the video (not a blocking modal — the party keeps playing/showing normally underneath), computing remaining time from the snapshot's absolute `deadline` against `Date.now() + clockOffsetMs` — reusing the clock offset the existing clock-sync handshake already maintains, not new client-side clock logic. The banner's label switches between "Next item in…" and "Playback pauses in…" based on the snapshot's `pending_transition.autoplay`, and disappears the moment a snapshot arrives without a `pending_transition` (fired or canceled) — the client never decides for itself when the countdown ends.

### 10.1 A real regression: auto-advance silently stopped firing, because "observation, not command" was true in prose only

A party configured with `auto_advance`/`show_next_dialog`/`autoplay_enabled` all on paused correctly at the very last moment of an item, then did nothing further, forever — no countdown banner, no advance. Pressing Play manually restarted the same item from position 0 instead of resuming or advancing. This reproduced 100% of the time, not intermittently.

**Root cause.** `player.js`'s native `<video>` `pause` listener forwarded *every* `pause` event as an authoritative `HandleControl(pause)` command, with no check for *why* the video paused. Per the HTML Living Standard, a `<video>` reaching the natural end of playback sets `paused = true` and fires `pause` (with `ended` already `true`) automatically — indistinguishable, to that listener, from the user clicking pause. So the moment a host's video hit its last frame, the browser's own automatic pause got forwarded to the server as a real host command, setting `p.state.IsPlaying = false` via `HandleControl`. `checkEndOfMedia`'s guard (`if !p.state.IsPlaying { return }`) then permanently blocked the very detection this depends on — no idle transition, no `enterPendingTransition`, ever, for that item. Not a race: the browser's automatic `pause` fires within milliseconds of the true end, while `SYNC_SNAPSHOT_INTERVAL` (the periodic tick that otherwise runs `checkEndOfMedia`) defaults to 4 seconds — the spurious client command always won. The "restarts from 0" symptom was a downstream consequence, not a separate bug: per spec, `video.play()` on an already-`ended` element seeks to 0 before resuming, and that 0 got forwarded and trusted verbatim by the (deliberately) host-trusting `HandleControl`.

This was a genuine spec-compliance gap, not a new design question: both this document (§9.1: "the host client's `ended` event is an observation, not an authoritative command") and `SPEC.md`'s Synchronization Protocol section stated this rule from the start. It was simply never implemented — no `ended` listener existed at all, and the `pause` listener that *did* exist didn't distinguish the two cases. The bug predates auto-advance entirely (the unguarded `pause` forwarding shipped with native-controls support, before playlists or Party Settings existed); it was invisible until end-of-media started meaning "maybe advance, maybe show a dialog" instead of just "pause," because "the browser paused early" and "the server decided to pause" used to look identical from the outside.

**Test coverage gap.** No test, Go or JS, caught this. `internal/party`'s `TestPendingTransition_*`/`TestEndOfMedia_*` tests all drive the actor directly via `HandleControl` and internal calls — they never simulated a client forwarding a premature pause, because that's not something the server does to itself. The actual defect lived entirely in `player.js`'s client-side event wiring, which had zero test coverage (no `player.test.mjs`, unlike `sync.test.mjs`/`playlist-select.test.mjs`).

**Fix, part 1 — stop forwarding the automatic pause.** The `pause` listener now checks `video.ended` (via a small extracted pure predicate, `isRealPause` in `playback-events.js`, unit-tested the same way `sync.js`/`playlist-select.js` separate pure logic from DOM-heavy code) and skips forwarding when the pause was the browser's own end-of-media pause, not a real user action.

**Fix, part 2 — closing the window between natural end and the next tick.** Simply not forwarding the spurious pause isn't enough on its own: the server can still believe `IsPlaying = true` for up to `SYNC_SNAPSHOT_INTERVAL` after the video actually ends, since `checkEndOfMedia` otherwise only runs on the periodic tick. During that window, any snapshot a client receives or reads while its own `<video>` is already paused-at-`ended` would make `applyAuthoritativeState` call `programmaticPlay()` → `video.play()` on an ended element — reproducing "restarts from 0" again, this time nondeterministically, via the sync path instead of a manual click. Two changes close this:

- **Event-driven detection.** A new observation-category wire message, `ended_hint` (`wsproto.MsgEndedHint`; see `SPEC.md`'s Synchronization Protocol section), is sent by the host's client on the genuine `video` `ended` event — not the `pause` event — and carries no payload and no authority. `Party.HandleEndedHint()` just re-runs `checkEndOfMedia` immediately (`p.do(func() { p.checkEndOfMediaAndBroadcast() })`) instead of waiting for the next tick. This is exactly what makes the client's `ended` event "an observation, not a command" for real: `checkEndOfMedia` recomputes everything from the server's own state/clock, so a stale, early, or even spoofed hint is a no-op if the server's own math disagrees. Deliberately not rate-limited or deduplicated — `checkEndOfMedia` is O(1), in-memory, and idempotent when there's nothing to correct, and this project's own stated scale (≤20 concurrent users per `CLAUDE.md`) makes even a misbehaving client resending it on every frame immaterial cost. If that assumption ever stops holding, rate-limit at that point, not preemptively here.
- **Defensive re-validation before every state read, not just the periodic broadcast.** `checkEndOfMedia` was cheap and already idempotent (guarded by `p.pending != nil` / `!p.state.IsPlaying`), but only `onSnapshotTick` was calling it before handing state to a client. A new shared helper, `checkEndOfMediaAndBroadcast()`, now runs it immediately before every broadcast that wasn't already the direct result of a state change in the same call: `onGraceTick`, `Leave`'s host-successor branch, `HandleHostTransfer`, and `UpdateSettings`. `Join()` and `Party.Snapshot()` — which don't broadcast, they hand a payload directly to one caller — each got their own direct `checkEndOfMedia()` call before building it. `Snapshot()` in particular is the single chokepoint behind six external callers (`embyreport`'s poll, `handleListParties`, `handleGetParty`, and the WS pre-join reauth check), so fixing it there covers all of them at once rather than requiring each to be found and patched individually — which is exactly how the first pass at this fix nearly missed `handleGetParty`. When `checkEndOfMedia` does find the end reached, it already broadcasts on its own (via `transitionCurrent`/`enterPendingTransition`); the caller's own subsequent broadcast just resends the same sequence number, which every client's existing staleness check (`sync.js#isStale`) already silently drops — so no call site needs to special-case "did it already act."

**A deliberate consequence worth naming plainly, not leaving implicit: `Snapshot()` is no longer side-effect-free.** A handful of read-only-looking endpoints — `handleListParties` (the dashboard GET, fires on every page load) and `handleGetParty` (a plain page refresh) in particular — can now trigger an authoritative state transition and a broadcast to every *other* connected member of that party, purely because someone loaded an unrelated page. This is correct and intentional, not a leak: the alternative (patching only the WS-facing broadcast call sites) is exactly what left `handleGetParty` exposed in the first place, since a plain page refresh is a more common trigger for this window than a WebSocket reconnect. `checkEndOfMedia` was already safe to call speculatively; folding it into the one function every reader of party state already goes through just extends the same guarantee `onSnapshotTick` already had to every reader, not only the periodic broadcaster. Any future caller of `Snapshot()` should not assume it's a pure read.

### 10.2 A second real regression: auto-advance loaded a broken player, not the next item

A party configured with `auto_advance`/`show_next_dialog`/`autoplay_enabled` all on would pause correctly near the end of an item, correctly show the "Next item in…" banner, then fail to load the next item at all — a persistent loading spinner and an on-screen `Playback error: mediaSourceRequiresReset`, hls.js's own fatal-error code for a `MediaSource` it can no longer use. This never reproduced on the very first item a page loads, only on a playlist transition to a second (or later) item.

**Root cause.** §9.6 extended `player.js` to re-fetch a playback URL and reload the source (`attachSource`) whenever a snapshot's `item_id` changes, re-arming the §5.8 calibration listeners per load — but never addressed what happens to the underlying `Hls` object itself across that reload. `attachSource` built `const hls = new Hls(); hls.attachMedia(video);` fresh on every call, with no reference kept anywhere and no teardown of whatever instance was already attached. On the very first load there's nothing preceding it to conflict with, so this looked fine. On a transition, `loadCurrentItem` first resets the `<video>` element (`video.pause(); video.removeAttribute("src"); video.load();`) while the *previous* `Hls` instance is still alive and still believes it owns that element's `MediaSource` — hls.js requires `destroy()` (which handles detaching internally) before anything else touches a media element it doesn't already know has been released. Then `attachSource` ran again and built a *second* `Hls` instance, `attachMedia`-ing onto the same `<video>` while the first was still alive with in-flight fragment/append work. Two live instances contending for one `MediaSource`, with the first one's state invalidated out from under it by the unguarded `video.load()`, is exactly what surfaces as a fatal `mediaSourceRequiresReset`. The same leak applied to any transcoded→direct-play or transcoded→idle transition too — those branches never touched the previous `hls` at all.

**Test coverage gap.** Same shape as §10.1's: `player.js` had — and still has, for everything except this one lifecycle rule — zero test coverage. It's DOM-heavy and runs `main()` as a module-load side effect, so it can't be imported under Node's test runner (no jsdom in this project) without extracting the logic worth testing, the same reasoning that produced `playback-events.js`/`isRealPause` out of §10.1's fix.

**Fix.** The `Hls` instance lifecycle is now owned by a small extracted module, `hls-source.js` (`createHlsInstanceManager()`), dependency-injected on the `Hls` constructor so it's unit-testable (`hls-source.test.mjs`) without a DOM or the real vendored library. `attach(HlsCtor, video, url, onFatalError)` unconditionally destroys whatever instance it's currently holding before constructing and attaching the next one; `destroy()` is exposed standalone too. `player.js` holds one manager at module scope and calls `hlsManager.destroy()` as the very first statement of `loadCurrentItem`, before the `<video>` element reset — covering the item-to-item transition, the transcoded→direct-play/native-HLS transition, and the item-to-idle transition (`item_id` → `""`, queue exhausted) with the same unconditional call, since it runs before `loadCurrentItem`'s own `if (!itemId) return`. `attachSource`'s hls.js branch now calls `hlsManager.attach(Hls, video, url, onFatalError)` instead of managing `new Hls()` inline.

**What this fix does and doesn't do.** On a fatal hls.js error, the manager destroys the broken instance and calls `onFatalError`, which `player.js` still wires to the same `showError("Playback error: " + ...)` as before — this guarantees clean teardown (no broken instance left attempting further recovery in the background, and no leaked instance for the *next* transition to collide with) but does not add retry or auto-rebuild logic. A genuine fatal HLS error (a real network failure, a truly corrupt stream) still just shows the same red error text with no retry, unchanged from before this fix. What changes is that a *normal* playlist transition no longer produces a spurious fatal error in the first place, since there's no more instance conflict to trigger one.

**A related observation investigated and deliberately not folded into this fix.** The same bug report described the *current* item pausing roughly 10 seconds before its actual last frame, just before the "Next item" banner appeared. `checkEndOfMedia` (party.go) was traced end to end: it's a pure comparison of `syncalg.ExpectedPosition(...)` (wall-clock extrapolation from the last authoritative state change) against `p.current.DurationTicks` (fetched once from Emby's `RunTimeTicks` at add-time, documented as authoritative — §9.5's schema), with no hardcoded margin or tolerance anywhere in `internal/party`/`internal/syncalg` that could explain a deterministic early cutoff. Two explanations fit without requiring a code bug: the added item's Emby-reported `RunTimeTicks` not precisely matching its actual playable/transcoded duration (external metadata this codebase correctly trusts, not a logic error here), or an earlier real playback stall that the server's wall-clock model — which has no visibility into client-side buffering — couldn't see, letting its linear extrapolation run ahead of the real video by the time it neared the end. This is a known, accepted tradeoff of "the server is authoritative" (`CLAUDE.md`'s hard invariant), not a regression. Patching `checkEndOfMedia` with a guessed tolerance to make this specific report go away was rejected as exactly the guess-patch this investigation was trying to avoid.

Rather than let that observation quietly disappear, `checkEndOfMedia` now logs at `LOG_LEVEL=debug` on every evaluation while a party is playing (not just when it trips): party ID, item ID, `expected_position_ticks`, `duration_ticks`, the state's own `position_ticks`/`is_playing`, milliseconds elapsed since the last authoritative state change, and whether this evaluation reached the end. So the next repro produces a trail — a gap already present early in playback points at a `duration_ticks`/actual-media mismatch; a gap that opens up suddenly points at an unseen stall — instead of another guess. This rides the same `Snapshot()`-driven `checkEndOfMedia` chokepoint §10.1 already established as the point every external reader passes through (`embyreport`'s poll, `handleListParties`, `handleGetParty`, the WS pre-join reauth check), plus the periodic `snapshotTicker` and each connected client's 30-second `clock_sync` ping (`logSyncDiagnostics`, which already logs from this same chokepoint at a comparable rate). Traced for one actively-playing party with `M` connected, actively-reporting members: `snapshotTicker` contributes 1 line per `SYNC_SNAPSHOT_INTERVAL` (default 4s, party-wide); `embyreport`'s poll contributes `M+1` lines per `EMBY_PROGRESS_INTERVAL` (default 10s — one call in `reportAllProgress` plus one per reporting member in `report()`); `clock_sync` contributes `M` lines per 30s (one per connected client). At this project's stated ≤20-concurrent-user ceiling (`CLAUDE.md`), the worst case — all 20 in one party — is roughly 3 lines/sec; a realistic single party (this being a small friends/family tool, per §7) is closer to 1 line/sec. Deliberately not sampled or rate-limited, same reasoning as §10.1's `ended_hint` note: gated behind `LOG_LEVEL=debug` (opt-in, never the default), and this project's stated scale makes that volume immaterial. If that assumption ever stops holding, rate-limit or sample at that point, not preemptively here.

## 11. Persistent sidebar, leave-on-navigate, and a resizable right sidebar

**The decision to make.** The party room lived in visual isolation from the dashboard: no left-hand nav, a standalone "Leave Party" button, and a right sidebar (Watching Now / Playlist / Chat) that just grew with content instead of behaving like a real dockable panel. The request: make the dashboard's sidebar persistent across every page (party room included, reusing its markup rather than forking a copy), replace the Leave button with "navigating away via the sidebar = leaving," and make the right sidebar's three sections independently scrollable, collapsible, and resizable, with state persisted across reloads.

### 11.1 A shared template partial, introduced for the first time

`index.html` and `party.html` were, until now, two fully independent templates with no `{{define}}`/`{{template}}` composition between them — `webassets.Templates()` (`template.ParseFS(templatesFS, "web/templates/*.html")`) parses every embedded `*.html` file into one shared template set, which made adding a partial trivial once one was actually needed. `internal/webassets/web/templates/_sidebar.html` defines `{{define "sidebar"}}...{{end}}`, included via `{{template "sidebar" .}}` from both pages. A new `pageData{PartyID, ActiveNav}` struct (`internal/httpapi/pages.go`) replaces the previous ad hoc `nil`/`map[string]string{"PartyID": ...}` passed to `ExecuteTemplate`, since the partial needs to know which nav item (if any) to mark `is-active` — `"home"` on the dashboard, empty on the party room, since none of today's destinations represent "you're in a party" specifically.

Reusing the sidebar on the party room is a layout change, not just a markup include: `party.html` didn't have an `.app-shell`/`.sidebar`/`.main-content` structure at all (the dashboard's own viewport-height-bounded, independently-scrolling shell from §7). `party.html` now wraps its existing `.party-topbar` + `.party-layout` content in the same shell (`<div class="app-shell">{{template "sidebar" .}}<main class="main-content party-main">...`), with a `.party-main` CSS modifier overriding the dashboard's own padding/overflow assumptions so the party page's topbar and layout keep owning their own scroll regions (see §11.3) instead of the whole page scrolling as one. The host-only Party Settings cog (`#party-settings-btn`) and its gating (`isHost()` in `player.js`) are untouched by this — it lives inside `.party-topbar`, which this change relocates but doesn't alter.

The left sidebar itself gained no new behavior in this pass — no collapse toggle was added to it. Despite the sidebar being colloquially described as "collapsible," no such mechanism existed in the markup/CSS/JS at this point; only the right sidebar's three sections (§11.3) were collapsible. (A collapse toggle for the left sidebar was added later — see §11.8.) `sidebar.js` (`initSidebar`) is the one shared module both `app.js` and `player.js` now import for the sidebar's user-avatar/name display and sign-out wiring, replacing what used to be duplicated directly in `app.js`.

### 11.2 Leave-on-navigate, and the disconnect/left bug it exposed

The party room's standalone "Leave Party" button is gone. In its place: navigating away from a party through the sidebar — a nav link click (in practice, only "Home" has a real destination today; Parties/History/Settings remain inert `is-coming-soon` placeholders) or signing out — now calls the same `POST /api/parties/{id}/leave` the old button called (`leaveCurrentParty` in `player.js`), awaited before the navigation/logout actually proceeds (`sidebar.js`'s `onBeforeNavigate` hook). This is deliberately scoped to what a sidebar click can reliably intercept: the browser back button, a tab close, and a hard refresh are **not** covered by this and continue to fall through to the existing disconnect-then-grace-period path — a `beforeunload`/`pagehide` handler can't guarantee the leave request completes before the page actually unloads, so it isn't a substitute for that path and wasn't added.

Signing out from the party room's sidebar was a real decision, not an assumed extension of "nav link": unlike a transient disconnect, a user can't undo signing out by simply reconnecting (their session cookie is gone), so recording it as `disconnected` would have no upside and would needlessly hold up host-grace-period timing and the member list's accuracy for everyone else until the inactivity sweep (§8) eventually cleared it. Sign-out was decided to go through the same explicit-leave path as a nav-link click.

**A real, pre-existing bug, found while tracing this path, not introduced by it.** `Party.Disconnect` unconditionally set `connection_status` to `disconnected`, with no check for whether the member already had `left`. Every leave — including the *old* Leave button, before any of this work — is followed by that same connection's own WebSocket closing (the browser navigating away tears down the socket either way), which runs `wsReadLoop`'s deferred `p.Disconnect()` (`internal/httpapi/ws.go`) on its way out. Without a guard, that silently downgraded a deliberate `left` back to `disconnected`, in memory and in SQLite — meaning the `connected`/`disconnected`/`left` distinction SPEC.md's "Connection state vs. intent" section describes was already broken for the one path meant to demonstrate it working, before this task touched anything. Fixed with one guard clause: `Disconnect` now no-ops if the member's `ConnectionStatus` is already `dbx.ConnLeft`. `TestDisconnect_DoesNotDowngradeAlreadyLeft` (`internal/party/party_test.go`) pins this: `Leave` followed by `Disconnect` on the same member must still read back as `left` via `Snapshot()`.

### 11.3 The right sidebar: independently scrollable, collapsible, resizable, persisted

`.party-sidebar-col` no longer scrolls itself — each of its three `.sidebar-block`s (Watching Now, Playlist, Chat) now has its own `.sidebar-block-header` (a clickable toggle) and `.sidebar-block-body` (`overflow-y: auto; min-height: 0`), so one section can be scrolled, collapsed, or resized without moving the others. The column's own bounded height comes from the same `min-height: 0`-chain technique §7 already established for the dashboard's independently-scrolling panes, extended one level deeper: `.party-main` (`height: 100%` inside the viewport-height `.app-shell`) → `.party-layout` (`flex: 1; min-height: 0`) → `.party-sidebar-col` (`overflow-y: hidden`) → each `.sidebar-block-body` scrolling on its own.

Collapse is a header click toggling `.sidebar-block.is-collapsed`, which hides the body and fixes that block's height to just the header. Resize is a `.sidebar-resize-handle` between each adjacent pair of *expanded* blocks — dragging trades height between that pair only (the standard split-pane behavior, not a three-way renegotiation), clamped at a `MIN_PANEL_HEIGHT` of 80px; a handle adjacent to a collapsed block is disabled, since there's nothing to negotiate against a fixed-height neighbor.

The resize math and collapse-toggle state transitions live in a DOM-free pure module, `sidebar-panels.js` (`resizePanels`, `toggleCollapse`, `loadPanelState`/`serializePanelState`), unit-tested in `sidebar-panels.test.mjs` without a DOM — the same split already established by `playlist-select.js`/`hls-source.js`/`playback-events.js` for keeping pointer/DOM-event wiring separate from the logic worth testing directly. `player.js`'s `initSidebarPanels` is the thin DOM/`localStorage` glue layer, wired at module load (like this file's other top-level listeners) rather than inside `main()`'s async flow, so a returning visitor's persisted layout applies as soon as the page paints instead of waiting on the `/api/me`/party-info round trips.

**Persistence is `localStorage`, per-browser — not a per-account server-synced preference.** This app has no other per-user-preference storage to extend, and a server round trip for a pure UI convenience (versus a functional/authorization concern) would be disproportionate to what's being solved. A stored value survives reloads on the same browser but doesn't follow the account to a different device/browser; if that turns out to matter in practice, it would need a small new endpoint/column, deliberately not built preemptively here.

### 11.4 Two stacked bugs, from merging §11.1's partial: every page loaded blank

Immediately after §11.1's shared-partial work merged, every page (`/` and `/party/{id}`) loaded as a completely blank document — not a rendering or JS problem, `view-source:` showed an empty `<body>` with nothing in it at all. `go build ./...` and `go vet ./...` both passed cleanly; the process itself started and logged `"listening"` normally. This turned out to be two independent bugs, stacked, each one hiding the other's symptom.

**Reproducing it.** Built the actual binary the way the Dockerfile does (`CGO_ENABLED=0 go build`, since a plain `go run`/`go build` under cgo hits an unrelated `privdrop` failure when run as root — see §6 — that would have blocked reproduction entirely), ran it, and requested `/`:

```
HTTP/1.1 200 OK
Cache-Control: no-cache
Content-Type: text/html; charset=utf-8
Content-Length: 0
```

Zero bytes in the body, `200 OK`, nothing in stderr. Exactly the reported symptom, and notably *not* a 500 — which is what made it look like a rendering bug rather than a server-side failure at first glance.

**Bug 1, the actual root cause: `//go:embed web/templates` silently dropped `_sidebar.html`.** Go's `embed` package excludes any file or directory whose name begins with `.` or `_` from a bare `//go:embed <dir>` pattern — this is documented behavior (the `all:` prefix is required to include them), not a bug in the `embed` package, but it's easy to miss for a file that's meant to be included precisely *because* its name marks it as a partial rather than a page. `internal/webassets/webassets.go`'s `templatesFS` used the bare form, so `_sidebar.html` — and the `{{define "sidebar"}}` template it declares — was never in the embedded FS in the first place. This has nothing to do with `template.ParseFS`'s glob (`*.html` matches `_sidebar.html` fine at the pattern level) or with any naming collision; the file simply never reached the parser.

Confirmed directly, not inferred from the diff: a throwaway program (later deleted — see below) called `webassets.Templates()` and printed what actually parsed:

```
Parsed templates:
 - party.html
 - index.html
```

No `sidebar` template at all. Executing either page against that set produced:

```
index.html exec err: html/template:index.html:41:17: no such template "sidebar"
party.html exec err: html/template:party.html:13:13: no such template "sidebar"
```

Both templates open their `<body>` with `{{template "sidebar" .}}` (party.html) or reach it within the first visible section (index.html) — essentially the first thing either template does — so `ExecuteTemplate` failed before writing any output at all, for both pages, on every request. This also answers a question worth ruling in/out explicitly: `mustParseTemplates()` does **not** panic at startup over this. Parsing a `{{template "sidebar" .}}` reference doesn't require "sidebar" to be defined anywhere in the set — `html/template` only resolves template names at execution time, not parse time. So the failure mode was "server starts fine, every page silently breaks," not "server won't start" — worth stating plainly since a startup panic would have pointed straight at the cause, and this didn't.

**Bug 2, independent, and what made bug 1 invisible instead of loud: both `ExecuteTemplate` call sites in `internal/httpapi/pages.go` discarded the returned error.**

```go
w.Header().Set("Content-Type", "text/html; charset=utf-8")
w.Header().Set("Cache-Control", "no-cache")
pageTemplates.ExecuteTemplate(w, "party.html", pageData{PartyID: r.PathValue("id")})
```

Headers (and, implicitly, the `200` status) were already sent before `ExecuteTemplate` ran, and its `error` return was never inspected. When execution failed immediately — as bug 1 guaranteed it would, on literally every request — nothing more was ever written to `w`, and Go's `net/http` had already committed to a `200 OK`. The result: a `200`, correct `Content-Type`, `Content-Length: 0`, and no error anywhere in the logs, because there was no code path that could have logged it. This is what turned "a template is missing" — which would normally be a loud, obvious failure — into a symptom indistinguishable from a JS/rendering problem until someone thought to check the raw response body.

These are genuinely two separate defects, not one bug described two ways: fixing only the `embed` directive would have made the pages render correctly, and the swallowed-error handling would have gone back to being simply unexercised, dormant code — correct in effect, but leaving the exact same silent-500-as-200 trap for the next template bug that comes along, whenever that is. Fixing only the error handling without the `embed` fix would have turned the blank page into a proper 500, which is a real improvement, but wouldn't have fixed the actual page.

**Fix.**
- `internal/webassets/webassets.go`: `//go:embed web/templates` → `//go:embed all:web/templates`, restoring `_sidebar.html` to the embedded FS.
- `internal/httpapi/pages.go`: a new `renderPage(w, logger, tmpl, name, data)` helper executes the template into a `bytes.Buffer` first. On error, it logs the real error (template name + `err.Error()` — safe to log; `pageData` carries only `PartyID`/`ActiveNav`, nothing that touches the credentials/tokens/session invariant in `CLAUDE.md`) and responds with a generic `500` body (`http.StatusText(500)`) — never the raw template error, which could otherwise leak internal template/file structure to a client. On success, headers are set and the buffered bytes are written in one shot. Both page handlers now call this helper instead of calling `ExecuteTemplate` against `w` directly with the headers pre-set. `registerPages` gained a `logger *slog.Logger` parameter (threaded from `RegisterRoutes`'s existing `app.Logger`) to support this.

**Test coverage.** Two new tests in `internal/httpapi/pages_test.go` exercise `renderPage` directly: `TestRenderPage_TemplateExecutionFailure_Returns500` (a deliberately broken template set produces a `500` with a generic body, and the real error still reaches the log) and `TestRenderPage_Success_ReturnsContent` (the real, production `pageTemplates` — including `_sidebar.html` — renders `200` with actual sidebar markup in the body; this one doubles as a regression test for the `embed` fix itself, since dropping the `all:` prefix again would fail this test with the exact `no such template "sidebar"` error above, not silently pass). `TestStaticAssetsAndPages_NotCacheable` (`app_test.go`), which already requested `/` and `/party/{id}` through the real mux, was extended to also assert a `200` status and a non-empty body — end-to-end coverage through `registerPages`'s actual wiring, not just the helper in isolation.

**Diagnostic tooling.** A throwaway `cmd/tmplcheck` program (calling `webassets.Templates()` directly and printing what parsed, then calling `ExecuteTemplate` to surface the real error text quoted above) was used to confirm the root cause before any fix was written, then deleted — it was never meant to be a permanent part of the tree, and isn't.

### 11.5 §5.7's fix silently stopped working: every host-only control in the party UI was visible to every participant

A host-only-UI audit (enumerating every element on the party page tied to a host-only backend action, checking each one's visibility against `isHost()`) found that `#party-settings-btn`, `#add-to-playlist-btn` (and therefore the entire "Add to playlist" browse dialog behind it — search, tabs, grid, series→season→episode drill-down, checkboxes, `#confirm-large-selection-dialog`), `#host-controls` (the Play/Pause row), and `#end-btn` were all visibly rendered for non-host participants — not just clickable-then-403, but present and unhidden from the moment the page loads, before any JS runs at all. This is precisely the bug §5.7 already fixed once, for `#end-btn` specifically: give the host-only control `hidden` by default in the markup, toggle it in `renderMembers`/`loadPlaylist` alongside `isHost()`. That mechanism is still in the code today, unchanged, correctly wired — `player.js`'s `endBtn.hidden = !isHost()`, `partySettingsBtn.hidden = !isHost()`, `hostControls.hidden = !isHost() || idle`, and `playlist.js`'s `addBtn.hidden = !isHostFn()` are all present and all run at the right times. None of it did anything.

**Root cause.** `style.css` never defined its own `[hidden]` rule. Browsers ship `[hidden] { display: none }` in their built-in user-agent stylesheet, but the CSS cascade orders declarations by *origin* before specificity: author-origin normal declarations always outrank user-agent-origin normal declarations, regardless of which selector is more specific or which rule appears later in the source. `.btn { display: inline-flex; ... }`, `.icon-btn { ...; display: flex; ... }`, and `.host-controls-row { ...; display: flex; }` are all author-origin rules that hard-code an explicit `display`. Any element carrying one of those classes — which is every one of the four controls above — keeps that `display` value even while its `hidden` attribute is set, because the UA stylesheet's competing `display: none` loses the origin comparison before specificity is ever consulted.

Verified empirically, not inferred from reading the cascade spec: a throwaway page (`button.btn` + `hidden`, next to a plain `button` + `hidden` with no class) was loaded in the actual Chromium binary this environment already vendors for Playwright (`/opt/pw-browsers/chromium`), and `getComputedStyle(...).display` read back for each:

```
{
  "b1": "inline-flex",   // .btn, hidden attribute set — still visibly displayed
  "b2": "none"            // no class, hidden attribute set — correctly display:none
}
```

Exactly the failure mode: an element with no conflicting `display` rule hides correctly; an element whose class also sets `display` does not, silently, with no console warning or any other signal.

**Test coverage gap.** No test caught this, and — matching §10.1/§10.2's shape — none could have without deliberately adding coverage for it. This project has no jsdom (`ARCHITECTURE.md` §1.6, §10.2), and jsdom would not have caught this specific bug even if present: jsdom's `getComputedStyle` reflects an element's own inline `style` attribute, not cascade resolution against a `<link>`/`<style>` stylesheet, so a jsdom assertion of `el.hidden === true` would have passed regardless of what a real browser actually renders — the JS-level toggle was always correct, only the CSS silently defeated it. Catching the actual rendered behavior requires a real browser engine, the same tool used to verify the root cause above. Introducing that permanently (Playwright or similar, plus the browser-binary install it needs) is a real infrastructure decision for a repo that currently has no `package.json`/`node_modules` at all — deliberately not taken on as part of this fix. What *is* added is a static-text regression test (`hidden-guard.test.mjs`) asserting the guarding CSS rule below is still present in `style.css` — a tripwire against the line being deleted or weakened, explicitly not a claim that it independently proves rendered behavior.

**A second, pre-existing gap this exposed:** the CI workflow's frontend test step ran `node --test internal/webassets/web/static/js/sync.test.mjs` by exact filename, not the `*.test.mjs` glob `CLAUDE.md` has always documented as the way to run these tests. `hls-source.test.mjs`, `playback-events.test.mjs`, `playlist-select.test.mjs`, and `sidebar-panels.test.mjs` all existed and all passed locally, but none of them had ever actually run in CI. Confirmed safe to fix before touching it: all four ran clean individually and together via the real glob (49 tests total across all five files, 0 failures) before `ci.yml` was changed. Fixed to the glob so `hidden-guard.test.mjs` — and the four files that were already there — actually run on every push and PR, not just locally.

**Fix.**
- `internal/webassets/web/static/css/style.css`: added `[hidden] { display: none !important; }` near the top of the file, right after the base reset. `!important` is load-bearing, not decoration — without it, the rule would still lose to `.btn`/`.icon-btn`/`.host-controls-row` on specificity grounds within the same (author) origin, since a class selector and an attribute selector both have specificity (0,1,0) and source order alone would leave this rule dependent on staying below every conflicting class in the file forever. One rule fixes all four broken controls at once, and guards against the identical mistake for any host-gated control added later — the alternative of writing `.btn[hidden]`, `.icon-btn[hidden]`, `.host-controls-row[hidden]` individually would need to be kept in sync with every future class that sets `display`, which is exactly the kind of per-site-discipline requirement that let this regress silently in the first place.
- `.github/workflows/ci.yml`: the frontend step's `run:` line changed from the single hardcoded filename to `node --test internal/webassets/web/static/js/*.test.mjs`.
- New `internal/webassets/web/static/js/hidden-guard.test.mjs` (static text assertion on `style.css`, see the test coverage gap note above for exactly what it does and doesn't prove).

No JS logic changed anywhere — `isHost()`/`isHostFn()` and every `.hidden = ...` call site in `player.js`/`playlist.js` were already correct and are untouched by this fix.

### 11.6 Chat, the last of the three sidebar blocks, didn't stretch to fill the column

Watching Now and Playlist sized correctly, but Chat — always the last `.sidebar-block` in `.party-sidebar-col` — stopped short of the column's bottom edge, leaving a gap that belonged to no panel (visible in a fresh session with no `localStorage` panel state, at any viewport tall enough for the sum of the three panels' heights to fall short of the column's own height).

**Root cause.** `.sidebar-block` (§11.3) sets `flex-shrink: 1; flex-grow: 0` — every one of the three blocks, Chat included. Each expanded block's height comes entirely from an explicit inline `flex-basis` px value `player.js`'s `applyPanelState` sets from `heightPx` (default or `localStorage`-persisted, per §11.3). With `flex-grow: 0` on all three, none of them ever claims space beyond that basis — when the column's actual height exceeds the sum of the three blocks' basis heights (plus the two resize handles and inter-block margins), the leftover space simply goes unclaimed below the last flex item. That's Chat, purely because of DOM/visual order, not anything specific to Chat itself. Confirmed empirically against a real Chromium instance (`/opt/pw-browsers/chromium`, per §11.5's precedent) rendering the actual sidebar markup and `style.css`: 309px of unclaimed space below Chat at 1920×1080 with default heights, reproducing with a simulated previously-resized user's smaller persisted heights too — so this is a general default-layout gap, not a `localStorage`/persisted-height interaction that `sidebar-panels.js`'s pure state logic needs to special-case.

**Fix.** `.chat-block.sidebar-block { flex-grow: 1; }`, added next to the existing `.chat-block .sidebar-block-body` rule. Watching Now and Playlist keep `flex-grow: 0`, unchanged, so their sizing (already correct) is untouched.

**Verified not to regress resize or collapse**, in both the fresh-session and previously-resized-user cases, against the real Chromium instance: dragging the playlist/chat handle still trades height between that pair pixel-for-pixel (the leftover `flex-grow` adds is a column-height-derived constant unaffected by the trade, since `resizePanels` conserves the pair's total exactly, per §11.3); dragging the watching-now/playlist handle leaves Chat's height untouched; a short viewport (sum of basis heights exceeding the column) still shrinks all three proportionally via the pre-existing `flex-shrink: 1`, since `flex-grow` only distributes *positive* leftover space and has no effect once there is none. Collapsing Chat itself is unaffected — `.sidebar-block.is-collapsed { flex: 0 0 auto !important; }` already overrides `flex-grow` along with everything else `.sidebar-block` sets.

**A known, pre-existing, narrower version of the same gap, deliberately not fixed here:** collapsing *Chat* leaves Playlist as the new last *expanded* block, and Playlist has no `flex-grow` — so the same unclaimed-space gap reappears below Playlist instead (526px in the same test setup). Confirmed present identically on the pre-fix code, so this isn't a regression introduced by the above — just the general "only the literal last block grows" fix not reaching the "last *currently expanded* block" case, which would need the grown block to be tracked as collapse state changes rather than fixed at `.chat-block` via CSS alone. Left out of scope for this fix; not filed as a separate tracked issue as of this writing.

### 11.7 Generalizing §11.6: leftover space follows whichever panel is last *expanded*, not a hardcoded one

§11.6 closed the gap for the one case that happened to matter at the time (Chat expanded, which is the common case), but flagged its own narrower blind spot: collapsing Chat hands "last block in the DOM" back to Playlist, which never had `flex-grow` either, so the identical unclaimed-space gap reopens underneath it (526px, confirmed present identically on `main` both before and after #27 — not a regression, just the fix's known reach). Any combination of collapsed panels reproduces the same class of gap under whatever panel is now last-and-expanded.

**Fix: derive the grow target from live collapse state instead of hardcoding it to one panel.** `sidebar-panels.js` gains `lastExpandedKey(state)` — a pure function, alongside `resizePanels`/`toggleCollapse`, unit-tested the same DOM-free way (`sidebar-panels.test.mjs`): walk `PANEL_KEYS` (`["watching-now", "playlist", "chat"]`) in reverse, return the first key whose `collapsed` is `false`, or `null` if every panel is collapsed. `player.js`'s `applyPanelState` — already the one place that reads panel state and touches the DOM on every load, toggle, and resize (§11.3) — calls it and toggles a new `.is-grow-target` class onto exactly that block, off every other one, on every state application. CSS drops the old `.chat-block.sidebar-block { flex-grow: 1 }` rule in favor of a generic `.sidebar-block.is-grow-target { flex-grow: 1; }`, which — like the rule it replaces — still loses to `.sidebar-block.is-collapsed { flex: 0 0 auto !important; }`, so a collapsed block never grows regardless of carrying the class.

**No interaction with resize or persisted heights, by construction.** `resizePanels` already conserves a dragged pair's total height exactly and only trades between two *expanded* siblings — `flex-grow` distributes whatever's left over *on top of* the explicit `flex-basis` px values `resizePanels`/`applyPanelState` already set, exactly the mechanism §11.6 verified against a real Chromium instance for the Chat-only case. Generalizing which panel carries the class doesn't change that mechanism, so this is a superset of the old behavior (identical result whenever Chat happens to be last-expanded) rather than a new interaction to re-verify from scratch. No `localStorage` schema change: `is-grow-target` is re-derived from the existing `{collapsed, heightPx}` shape on every `applyPanelState` call, not persisted itself.

The static-text regression tripwire for this (following §11.5's `hidden-guard.test.mjs` precedent — a real rendered-flexbox assertion would need a browser engine this project doesn't carry, see that section) moved from `chat-panel-grow.test.mjs` to `sidebar-grow-target.test.mjs` and now also pins that `player.js` actually derives the class from `lastExpandedKey` rather than a hardcoded key, alongside the CSS-rule check the old test already did.

### 11.8 The left sidebar becomes collapsible: an icon-only rail, independent of the right sidebar's collapse mechanism

§11.1 explicitly noted the left sidebar had no collapse mechanism, distinct from the right sidebar's per-panel collapse/resize (§11.3). This adds one: a toggle button (`#sidebar-collapse-toggle`, in `.sidebar-top` next to the brand mark) that switches the whole left sidebar between its normal full width (icons + labels) and a narrow icon-only rail (`--sidebar-w-collapsed: 72px`, vs. the normal `--sidebar-w: 232px`), applying on both pages that render `_sidebar.html`.

**Mechanism.** A single class, `.sidebar.is-collapsed`, toggled on the `<aside class="sidebar">` itself — not on `.app-shell` — since `.main-content`/`.party-main` are already `flex: 1; min-width: 0` (§7, §11.1) and reflow automatically as the sidebar's width changes; neither needed any adjustment. `.sidebar` gets a `transition: width 0.15s ease` (disabled under `prefers-reduced-motion`, matching the `.pulse-ring` precedent), while nav-item/brand/user-block text labels and the coming-soon badge hide via plain `display: none` rather than animating — an instant, not eased, change avoids any text-reflow flash mid-transition. `.nav-label-group` (the coming-soon items' icon+label wrapper) is itself a `<span>`, so the label-hiding selector is `.nav-item > span:not(.nav-label-group)` plus a separate `.nav-label-group > span` rule — a plain `.nav-item > span` selector would have hidden the wrapper (icon included), not just the label.

**State logic and wiring.** `sidebar-collapse.js` is a new DOM-free pure module (`defaultCollapsedState`, `loadCollapsedState`, `serializeCollapsedState`), unit-tested in `sidebar-collapse.test.mjs` the same tolerant-parse-with-fallback way `sidebar-panels.js`/`sidebar-panels.test.mjs` cover the right sidebar's state — sized down to a single boolean rather than `sidebar-panels.js`'s per-panel-key shape, so it skips a dedicated `toggleCollapsed` wrapper (negating a boolean inline in the DOM glue doesn't earn a named function the way the multi-key `toggleCollapse` does). The DOM/`localStorage` glue lives in `sidebar.js`'s `initSidebar` — the one module both `app.js` and `player.js` already import for the shared left sidebar — rather than in the right sidebar's `sidebar-panels.js`/`player.js` glue, which this feature doesn't touch. State (`localStorage` key `watchparty:sidebarCollapsed`) is loaded and applied synchronously at the top of `initSidebar()`, which both entry points call at module-eval time, before either page's `/api/me`/party-info round trip — the same early-apply timing `initSidebarPanels()` established for the right sidebar's persisted state (§11.3), so a returning visitor's collapsed rail is on screen at first paint rather than flashing expanded first.

**Accessibility.** `#sidebar-collapse-toggle` carries `aria-expanded` (reflecting whether the sidebar's labeled content is currently exposed) and `aria-label` (it's icon-only, so it needs an accessible name), both flipped — `aria-expanded="true"`/`aria-label="Collapse sidebar"` vs. `aria-expanded="false"`/`aria-label="Expand sidebar"` — by the same `applyCollapsedState` helper that sets the CSS class, on both the initial early-apply and every click, so a persisted collapsed state reads correctly to assistive tech from first paint too. Each `.nav-item` also gained a `title` attribute matching its visible label, for a native hover tooltip once the label itself is hidden — a small addition beyond what collapsing strictly required, not something the feature depends on.

**Deliberately unchanged.** No new responsive/narrow-viewport behavior: the sidebar had none before this (no `@media` rule anywhere touches `.sidebar`/`.app-shell`), so the collapse toggle stays an independent manual control, not tied to viewport width. The right sidebar's `sidebar-panels.js`/`sidebar-panels.test.mjs` are untouched — same pattern, deliberately not the same module, since the two sidebars' state shapes (one boolean vs. three `{collapsed, heightPx}` entries) don't share enough to unify without forcing an awkward abstraction over both.

## 12. Party chat: real-time messaging, membership-authorized, ephemeral

**The decision to make.** The mockup's Chat panel (§7) was stubbed with `.is-coming-soon` from the start. Building it for real touches this codebase's authorization posture more than any prior feature: every existing mutation (`HandleControl`, `HandleHostTransfer`, `AddPlaylistItem(s)`, `RemovePlaylistItem`, `ReorderPlaylist`, `SelectCurrentItem`, `UpdateSettings`) is gated to the host, per `CLAUDE.md`'s invariants. Chat has to be open to every member — that's the whole point of the feature — so it's the first exception, and a deliberate one rather than a loosened rule: every other mutation stays exactly as host-gated as before. Five things were decided; each is covered below.

### 12.1 Schema

```sql
CREATE TABLE chat_messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    party_id TEXT NOT NULL REFERENCES parties(id) ON DELETE CASCADE,
    user_id TEXT NOT NULL REFERENCES users(id),
    body TEXT NOT NULL,
    sent_at TEXT NOT NULL              -- RFC3339Nano, server-assigned
);
CREATE INDEX idx_chat_messages_party_id ON chat_messages(party_id, id);
```

No display name or avatar column, by design — see §12.5. `id` is a plain autoincrement, the same reasoning as `playlist_items.id` (§9.5): never exposed unguessably on its own, always reached under `/api/parties/{partyID}/chat`, which already requires the requester to be authenticated and the party to be active.

### 12.2 Transport and authorization: a new WebSocket message category, not REST

Chat needs to push to every other connected member regardless of how a message was submitted, and this app has exactly one push channel — the party's WS broadcast. Building it as a REST POST would still need to broadcast the result over WS afterward, which is pure duplication; so `chat_send` (client → server) / `chat_message` (server → broadcast) are new `wsproto.MessageType`s, riding the same connection every other message type already uses.

This doesn't fit any of the four existing categories from `SPEC.md`'s Synchronization Protocol section — it's not host-only like a Control event, and unlike an Observation event (`ended_hint`) it carries real authority: once accepted it's persisted and becomes part of the party's chat history, not just a hint the server may or may not act on. It's documented as a fifth category: **Chat events**, structurally like Control events (validated, sequenced-in-effect by the actor, and broadcast) but authorized by party **membership** instead of host status.

**Protection mechanism: Origin validation, not CSRF.** `handleWebSocket` already authenticates the session cookie and validates `Origin` once, at connection upgrade; every message type dispatched over that connection — including `chat_send` — rides that same already-authenticated, already-Origin-checked socket. No new CSRF surface was needed: CSRF in this codebase protects cookie-authenticated cross-origin REST POSTs specifically (`withCSRF`), which chat send never touches.

**Client behavior: no optimistic local echo.** Consistent with this codebase's "every client, including the acting one, reacts to the broadcast, not its own local action" discipline for playback state, the sender doesn't render their own message until the `chat_message` broadcast comes back over the same socket — not a special case, just the normal flow.

**Test coverage: a real WebSocket-wire integration test, not just actor-level ones.** Every other chat test in `internal/party/chat_test.go` calls `Party.HandleChatSend` directly, or exercises it via `fakeConn` — this is the same pattern `SPEC.md`'s own "Integration tests" line for play/pause/seek already uses ("against the real party actor"), and it's the pattern every existing `TestIntegration_*` test in `party_test.go` follows. None of that reaches `internal/httpapi/ws.go`'s actual `case wsproto.MsgChatSend:` dispatch arm, real JSON envelope framing, or a real socket. `TestWebSocket_ChatSend_BroadcastsOverRealSocket` (`internal/httpapi/app_test.go`) closes that gap: two independent `nhooyr.io/websocket` client connections (not `fakeConn`) against the real `httptest.Server`/`RegisterRoutes` mux, one sends a real `chat_send` envelope over the wire, and the assertion is that *both* connections — sender included, per the no-optimistic-echo rule above — receive a `chat_message` envelope back with the correct `user_id`/`body`, decoded through real JSON on both ends. This is the first WS-wire-level test of any kind in this codebase's history (confirmed: no prior test, for chat or any other message type, ever called `websocket.Dial`) — a genuinely new pattern, not a pre-existing one this PR is merely following, since none existed to follow.

### 12.3 The authorization departure

`Party.HandleChatSend` is dispatched through the actor exactly like every other mutation (`do()`-serialized, validated before mutating, broadcast afterward) — the *mechanism* is unchanged. Only the *policy* differs: instead of `userID != p.hostUserID`, `HandleChatSend` checks `_, ok := p.members[userID]; !ok` and rejects with `ErrNotMember`. A `chat_send` can only reach `HandleChatSend` via an already-`Join`-validated, already-Origin-checked WebSocket connection (`httpapi/ws.go`'s `dispatchWSMessage`), so the connection lifecycle already makes a foreign `userID` unreachable here in practice — the same reasoning `HandleEndedHint`'s doc comment uses for why it needs no authorization of its own. The explicit `p.members` check is still there, as **defense-in-depth, not the primary guarantee**: every other mutation in this codebase (`HandleControl`, `AddPlaylistItem`, etc.) performs its own runtime authorization check inside the actor regardless of how it's reached, rather than relying solely on caller discipline one layer up in `httpapi`, and chat's authorization should hold to that same pattern even though its *policy* (membership, not host) is narrower. `TestHandleChatSend_NeverJoinedRejected` (`internal/party/chat_test.go`) pins this directly — calling `HandleChatSend` with a `userID` that never called `Join` and asserting `ErrNotMember`, with no message persisted.

> **Revision note:** an earlier version of this section, and of `HandleChatSend`'s own doc comment, said there was "no explicit membership check here beyond 'party not ended'," relying entirely on the WS dispatch path's structural guarantee. A review pass flagged that as the one mutation in this codebase with zero redundant authorization — unlike `HandleControl`, which checks host status explicitly even though it's *also* only reachable the same structurally-gated way. The check above was added specifically to close that gap, for consistency with the rest of the codebase's pattern, not because the structural guarantee itself was found to be insufficient (it wasn't — the check is genuinely unreachable in production today, confirmed by `TestWebSocket_ChatSend_BroadcastsOverRealSocket` in §12.2 exercising the real path end-to-end).

Chat gets this narrower tier specifically because it doesn't touch anything the host-only invariants protect: it doesn't move playback state, doesn't change the playlist, doesn't call Emby. Gating it to the host would defeat the feature's entire point — everyone should be able to talk — whereas every other mutation is host-gated because it changes state all participants are forced to observe/sync to. No other mutation's authorization changed.

### 12.4 Server-side enforcement: length and rate limiting

The 300-character limit and the 2-messages/second-per-user rate limit are both enforced inside `Party.HandleChatSend`, independent of anything the client does — the client's own `maxlength` and 500ms post-send UI throttle are conveniences, not the actual boundary.

**Length** is checked with `utf8.RuneCountInString`, not `len()` — a multi-byte emoji must count as one character against the 300 limit, the same way a client's own (UTF-16-code-unit) length check would, not several bytes. An over-length message is **rejected with an error frame to the sender** (`wsproto.ErrCodeChatMessageLong`) — a compliant client's own `maxlength` should make this unreachable, so hitting it server-side means a bypassed or buggy client, worth surfacing.

**Rate limiting** is a token bucket per `(partyID, userID)`: capacity 4, refilling at 2 tokens/sec — a small burst allowance on top of the sustained "effective 2 messages/second" the requirement asked for, not an instantaneous 500ms gate. A message that fails the rate limit is **dropped silently, with no error frame**: a compliant client's own local throttle means this is essentially only ever hit by an actual flood (or a same-account multi-tab edge case), and echoing an error back to a flooding client would just hand it a fast tuning signal for its send rate — the same posture `HandleEndedHint` already takes toward a spoofed/stale hint ("simply a no-op").

**The burst allowance was reviewed specifically for a reconnect-abuse vector, and closed.** An earlier design deleted a user's bucket entry on `Leave`, "to bound memory." That's a real bypass: leaving and rejoining gets a fresh full-capacity bucket, turning a 2/sec sustained cap into "4 free messages per reconnect," and reconnects are cheap and unthrottled anywhere else in this codebase. The fix (`internal/party/chatlimit.go`): a user's bucket is **never deleted for the life of the Party actor** — not on `Leave`, not on `Disconnect`, not on rejoin — keyed by `userID` alone (not by connection, so a second tab from the same account shares the same bucket too). The whole `map[string]*chatBucket` is discarded only when the actor itself stops, the same lifecycle boundary chat history uses. The one way to get a fresh bucket is joining a *different* party — a different room with its own separate history and audience, which is the intended per-party scope, not a bypass of it. `TestChatRateLimit_ReconnectDoesNotResetBucket` and `TestChatRateLimit_DisconnectReconnectDoesNotResetBucket` (`internal/party/chat_test.go`) pin this directly: exhaust the bucket, leave/disconnect and rejoin, and assert the very next send is still rejected — only after a real elapsed refill window does a send succeed again. `TestAllowChatSend_ReusesExistingBucketAcrossCalls` separately pins that the lookup is a genuine get-or-create, not an accidental "always construct a fresh bucket" that would silently defeat the whole limiter while passing a casual manual test.

Both the length check and the rate limiter run inside the actor's `do()` (fast, IO-free) before the SQLite write, following the exact two-phase dispatch `AddPlaylistItem` (§9.3) established for a mutation that needs a blocking write but must never block the actor goroutine: authorize/validate fast inside `do()`, write in the caller's goroutine outside `do()`, then a second fast dispatch broadcasts the assigned id/timestamp. `MaxChatMessageLength` (Go) and `MAX_CHAT_MESSAGE_LENGTH` (`chat-format.js`) are kept in sync by convention, not a shared build step — the same "mirrored, not shared" approach §1.6 already takes for the sync math.

### 12.5 Retention: hooked into the one path every party-ending route already shares

All of a party's chat history is deleted the instant it transitions to `ended`. `Hub.EndParty` — called by both the explicit "End Party" HTTP handler and `Hub.SweepInactiveParties` (§8) — is the single funnel every way a party can end already goes through, calling `Party.End`. The retention hook lives there, next to `End`'s existing *synchronous* `UpdatePartyStatus` call (deliberately not fire-and-forget, since `End` already treats durability here as worth a blocking write): `store.DeleteChatMessages(ctx, p.ID)`, log-and-continue on failure rather than folding into `End`'s own error — a party failing to fully end because chat cleanup hiccuped would be worse than a rare leftover row. Because there's exactly one path, this required no new call site at either of the two places a party can end, and `TestSweepInactiveParties_DeletesChatMessages` pins the automatic-sweep path specifically (not just the explicit-end path), since "it goes through the same function" is easy to believe without a test that actually exercises it.

Party rows themselves are never deleted (`status` just becomes `ended`, permanently) — chat can't ride an `ON DELETE CASCADE` off the party row, so this has to be an explicit delete, not a side effect of anything else.

### 12.6 Display identity: resolved live, per viewer, like item titles and posters

`chat_messages` carries only `user_id` — no display name, no avatar. Rendering a message's sender identity is a new backend-routed endpoint, `GET /api/emby/users/{id}`, extending the exact pattern `GET /api/emby/items` established (§9.4): it calls Emby using the **requesting viewer's own** decrypted token, never a shared one, mirroring how playlist item titles are already resolved per viewer rather than persisted once. `emby.Client.GetUser` (`GET /Users/{id}`) returns the target's name and whether they have a `PrimaryImageTag`; `emby.Client.UserImageURL` builds a ready-to-use, `api_key`-bearing avatar URL the same way `ImageURL` already does for poster art, for the same two reasons (§9.4): an `<img src>` can't set custom headers, and a small profile thumbnail isn't what the no-proxy invariant is protecting. Avatar bytes never pass through this server, exactly like poster bytes don't.

**Flagged assumption, the same caveat this package already carries for its other endpoint-shape guesses (§9.4, §9.7):** whether a non-admin token can read *another* user's `/Users/{id}` profile depends on that Emby server's own policy configuration — some installs restrict this to admins. `handleGetEmbyUser` treats a failed lookup as "fall back to the display name already cached locally in this app's own `users` table" (populated at that user's own last login — pre-existing data, not a new copy made for chat) with no avatar, rather than failing the request; a chat message's identity should never block on this. `TestHandleGetEmbyUser_FallsBackToLocalDisplayNameOnEmbyFailure` pins the fallback path directly.

The client (`chat.js`) memoizes resolved `{displayName, avatarUrl}` per `user_id` in an in-memory `Map` for the page's lifetime — not `localStorage`, no persistence requirement here — so a repeat sender costs one Emby round trip, not one per message; a pending lookup's own Promise is cached too, so two messages from the same not-yet-resolved sender arriving close together share one in-flight request instead of firing a duplicate.

### 12.7 History and frontend

`GET /api/parties/{id}/chat` returns the most recent 200 messages, oldest-first, raw (`{id, user_id, body, sent_at}`, no identity) — membership-gated only by ordinary authentication, the same visibility rule `handleGetParty`/`handleGetPlaylist` already apply ("every active party is visible to every signed-in user," §7). No pagination: chat is ephemeral (wiped entirely at party end, §12.5) and this app's ≤20-concurrent-user scale doesn't call for a cursor API — a fixed recent window is simpler and was chosen deliberately over one.

`chat-format.js` holds the pure logic (`validateChatBody`, mirroring the server's trim/empty/length checks so an obviously-doomed send doesn't round-trip first; `truncateForOverlay`, the "first 50 characters" helper a later fullscreen-overlay PR reuses) — DOM-free and unit-tested, the same split `playlist-select.js`/`sidebar-panels.js` already established. `chat.js` is the DOM/network glue: composer wiring, history load, per-sender identity resolution/rendering, and a `sendChatMessage`/`handleIncomingChatMessage` pair exported specifically so a later fullscreen quick-reply overlay can submit through the exact same validation/throttle/transport path instead of duplicating any of it, and an `onMessage` hook so that overlay can observe incoming messages without this module needing to know fullscreen exists at all.

## 13. Fullscreen chat overlay and quick reply

**The decision to make.** A participant watching in fullscreen has no way to see chat at all — the sidebar panel it lives in isn't part of the fullscreen element. The request: a small, non-blocking toast-style overlay near the bottom-right of the video showing new messages, with a quick reply, that doesn't get in the way of watching.

### 13.1 A necessary prerequisite: fullscreen had to stop targeting `<video>` directly

`fullscreenBtn`'s click handler used to call `video.requestFullscreen()` on the bare `<video>` element. The Fullscreen API only keeps the *requested* element and its descendants rendered while fullscreen — an overlay as a sibling of `<video>` would simply not exist on screen during fullscreen, full stop, no CSS fix available. This had to change before an overlay could be built at all, not as an optional nicety.

The fix uses an element that already existed for exactly this shape of problem: `.player-frame` — `position: relative`, wraps `<video>`, and already hosts one absolutely-positioned overlay (`.next-item-banner`, the end-of-media countdown pill, §10). The chat overlay was added as a second child of `.player-frame` following that same established pattern, and `.player-frame` (not `<video>`) became `fullscreenBtn`'s fullscreen target — no new wrapper div introduced, since one already did the job.

**A second-order consequence, caught by testing rather than assumed away: video stretching instead of letterboxing.** Fullscreening `<video>` directly gets special browser handling — a fullscreened video element letterboxes to its intrinsic aspect ratio automatically. Fullscreening a plain `<div>` gets no such treatment; without `object-fit` set, `.player-frame video`'s existing `width:100%; height:100%` would *stretch* the video to fill whatever aspect ratio the fullscreen viewport happens to have, distorting it on any screen that doesn't happen to match the source's aspect ratio. Fixed with `object-fit: contain` on `.player-frame video` — applied unconditionally (not scoped to `:fullscreen`), since it's strictly safer in the normal in-page case too and was never a behavior worth keeping. `.player-frame:fullscreen { width: 100%; height: 100%; }` is also asserted explicitly rather than relied on implicitly from the browser's own `:fullscreen` UA styles, so `.player-frame`'s own `aspect-ratio: 16/9` can't end up constraining it once it's the element filling an arbitrarily-proportioned screen.

**iOS Safari: unaffected, and still a known, unavoidable gap.** `video.webkitEnterFullscreen()` — the legacy prefixed fallback for iOS Safari, which only supports fullscreening the `<video>` element itself, no container equivalent — is untouched, still called on `video` directly, not `.player-frame`. This means the chat overlay categorically cannot render during iOS native fullscreen; there is no code path that could make it. Documented as a known platform limitation, the same posture this app already takes for the playlist drag-and-drop feature's desktop-only reach (§9.6), not treated as a bug to chase.

### 13.2 What this was verified against, in a real browser, before landing

This area of the codebase (native `<video controls>`, `hls-source.js`'s instance lifecycle, fullscreen CSS) has broken in subtle, hard-to-predict ways multiple times before (§5.5, §5.8, §5.10, §10.2) — so this change was verified directly against a real, rendered Chromium instance (`/opt/pw-browsers`, the same tool §11.5/§11.6 already established for exactly this class of risk) rather than treated as routine. A minimal fixture reproducing the real `.player-frame`/chat-overlay markup and the actual `style.css`, `chat.js`, `chat-format.js`, and `chat-overlay.js` files (served over a local HTTP server so real ES module imports work, with `fetch` mocked so identity resolution didn't need a live Emby server) was driven end-to-end:

- **Fullscreen targets `.player-frame`, confirmed, not assumed:** `document.fullscreenElement` is `.player-frame` after clicking Fullscreen, never `<video>`.
- **Native video controls unaffected:** `video.controls` stays `true` and the element renders with nonzero size in fullscreen — nothing about becoming a descendant of the fullscreen element (rather than being it) changes how the browser draws its native controls.
- **Letterboxing verified, not just styled:** `getComputedStyle(video).objectFit` reads `contain` in fullscreen, and `.player-frame`'s rendered bounding box matches the viewport exactly (`aspect-ratio: 16/9` does not leak through and constrain it) — the stretching regression described in §13.1 was reproduced first (this rule deliberately omitted) and confirmed fixed by adding it back.
- **`hls-source.js`'s instance lifecycle is untouched, confirmed by what *didn't* change:** this PR does not modify `hls-source.js` or `playback-events.js` at all, and neither file references `.player-frame`, fullscreen state, or any DOM ancestry of `<video>` (`grep`-confirmed) — both already operate purely off the `<video>` element reference itself, which keeps the same `id="video"` and is found the same way (`document.getElementById("video")`) regardless of which element wraps it or which one is fullscreen. `hls-source.test.mjs`'s existing suite (unmodified, still passing) is the same logic exercised the same way either side of this change.
- **Enter/exit fullscreen behavior unchanged apart from the overlay:** clicking Fullscreen still enters fullscreen the same way; exiting (via the browser's native exit, exercised as `document.exitFullscreen()`) correctly clears `document.fullscreenElement` and, new in this PR, also dismisses any showing overlay (`fullscreenchange` listener) rather than leaving a stale card floating over the now-windowed player.
- **The overlay itself, end-to-end:** hidden by default; shown (with the resolved sender name and a body truncated to 50 chars + `…`) for another user's message while fullscreen; *not* shown for the viewer's own message; dismissed by the manual × button; auto-dismissed after the stated ~6s specifically once no longer hovered, and confirmed to **not** dismiss while still hovered past that window (real timing, not simulated); a submitted quick reply clears the input and dismisses immediately, confirmed to go through `chat.js`'s real `sendChatMessage` (the fixture included the sidebar composer's own DOM elements specifically so this exercised the actual shared code path, catching a fixture-only gap on the first pass before that was added — the composer-disable side effect `sendChatMessage` triggers depends on those elements existing, which they always do on the real party page).

**What was not verified live, and why:** iOS Safari's `webkitEnterFullscreen` path has no engine available in this environment to exercise — confirmed only by code inspection (the call site and its branch are byte-for-byte unchanged, still targeting `video` directly, not `.player-frame`), consistent with this PR's own documented limitation that the overlay can't render there regardless.

### 13.3 Dismiss behavior

Chosen as a specific combination, not left as an open question: auto-dismiss ~6 seconds after the last interaction; hovering the card or focusing the reply input pauses the timer for as long as that lasts, restarting a **fresh** 6-second window once it ends (not resuming a partial one — simpler, and arguably the more correct read: "you looked away again" deserves a full fresh window, not a continuation); a manual × always dismisses; a successful reply send dismisses immediately regardless of the timer; a newer incoming message replaces whatever is currently showing and resets the timer, so only one overlay is ever visible at a time.

### 13.4 Trigger condition and code organization

`shouldShowOverlay(isFullscreen, senderUserId, viewerUserId)` (`chat-format.js`) is the pure predicate: shown only while actually fullscreen, and never for the viewer's own message. `chat-overlay.js` is the DOM/timer glue around it — the same pure/glue split every other module pair in this app uses. It reuses `chat.js`'s `resolveIdentity` (exported specifically so the overlay doesn't fire a second, duplicate Emby lookup for a sender the sidebar panel has already resolved or is already resolving) and `sendChatMessage` (so the quick reply is subject to the exact same 300-char/rate-limit/500ms-local-throttle path as the sidebar composer, not a second implementation of any of it) and `truncateForOverlay` for the 50-character preview. `.player-frame:not(:fullscreen) .chat-overlay { display: none !important; }` is a defense-in-depth CSS guard on top of the JS check — even a bug in `shouldShowOverlay`'s call site couldn't make the overlay physically render outside fullscreen.
