# CLAUDE.md

Durable working rules for this repo. Keep this short — for the reasoning behind any non-obvious decision, read `ARCHITECTURE.md`, not here. For the full product spec and where the build diverged from it, read `SPEC.md`.

## Tech stack

- **Backend:** Go, stdlib `net/http` + `nhooyr.io/websocket`. No web framework.
- **Persistence:** SQLite via `modernc.org/sqlite` (pure Go, no CGO), migrated with `golang-migrate` (`internal/dbx/migrations`).
- **Frontend:** Server-rendered HTML + vanilla JavaScript. No framework, no bundler, no build step — files under `internal/webassets/web/static` are served as-is.
- **Container:** Multi-stage Dockerfile, static binary, distroless final stage (no shell). Target both Docker Compose and Podman quadlet; nothing Docker-socket-specific.

## Hard invariants

These must never be silently violated. If a change requires bending one, stop and flag it explicitly rather than working around it quietly.

- **The server is authoritative for playback state.** The host's client issues *requests* (play/pause/seek); it is never trusted as the source of truth. Every authoritative state change is validated, timestamped, sequenced, and broadcast by the party actor (`internal/party`), and every client — including the host's own — reacts to that broadcast, not to its local action.
- **Client-supplied Emby `PositionTicks` are never forwarded to Emby.** Any position reported to Emby (`Sessions/Playing*`) must be server-derived from the party's authoritative state (`syncalg.ExpectedPosition`), never taken verbatim from a client message. Client-reported position may be logged for diagnostics only.
- **Watch Party never proxies, caches, or transcodes media.** The server hands back an Emby-constructed playback URL; the participant's own browser streams directly from Emby using that participant's own token. No media bytes ever pass through this server.
- **Emby credentials, tokens, session cookies, and authenticated playback URLs are never logged — at any log level, including debug.** There is no automated redaction; this is enforced by not putting these values in a log call in the first place. Before adding a log statement near auth, sessions, or `emby.Client`, check what you're passing.
- **Media authorization is re-validated per participant, for whatever item is currently loaded — not inherited from the host, and not just checked once at join.** A party's current item can change after join (playlist advance, or a host selecting a different item), so the check re-fires every time it does, at the point each participant fetches a playback URL for it (`handlePlaybackURL`) — not only at the join-time gate, which only covers the item current *at that moment*. Being the host, or another member already having access, never implicitly grants anyone else access to an item they couldn't already see in Emby themselves.
- **Every party mutation is host-gated, except chat send.** `HandleControl`, `HandleHostTransfer`, every playlist mutation, and `UpdateSettings` all check `userID == p.hostUserID`. Chat (`HandleChatSend`) is the sole, deliberate exception — authorized by party membership instead, because it doesn't touch playback state, the playlist, or Emby (see `ARCHITECTURE.md` §12.3). Don't extend membership-only authorization to any other mutation without equally deliberate design and a documented reason — the host-only pattern is the default for a reason.
- **Page routes are session-gated server-side, not just client-side-toggled.** `GET /` and `GET /party/{id}` (`internal/httpapi/pages.go`) call `app.Sessions.Authenticate` before rendering — an unauthenticated `GET /` never contains `home-section`'s markup at all (gated in the template via `pageData.Authenticated`), and an unauthenticated `GET /party/{id}` redirects to `/` rather than rendering. This was previously missing entirely (see `ARCHITECTURE.md` §16.26) — the client-side JS toggle (`app.js`'s `showHome`/`showLogin`) is not itself an auth boundary, just a UX convenience layered on top of one. Any new server-rendered page route needs the same session check; don't assume the JS toggle is sufficient. The same trap recurs on the way *out* of an authenticated page, not just on the way in: a session-ending action (logout) must navigate to a fresh server-rendered page rather than hiding already-shipped authenticated markup in place, or that markup — validly rendered while the session was still good — outlives the session in the live DOM (`ARCHITECTURE.md` §16.27). `app.js`'s and `player.js`'s `onLoggedOut` handlers must always end in `window.location.href = "/"`, never a same-page `hidden`-attribute toggle. `onLoggedOut` itself, however, must only be *called* once the session is actually confirmed gone (a `204` from `POST /api/auth/logout`, or a `401` meaning the server already agrees there's no session) — never unconditionally on any failure of that request, since a `403`/network failure doesn't mean the session was invalidated, and navigating to `/` in that case would just silently re-render a still-authenticated page as if signing out had worked. See `ARCHITECTURE.md` §18.
- **No secrets in `config.jsonc`.** `TOKEN_ENCRYPTION_KEY`/`TOKEN_ENCRYPTION_KEY_FILE` are resolved from the environment only, never from the config file (`internal/config.FileConfig` has no field for it, and any attempt to set one is rejected as an unknown field). The setup wizard (`internal/httpapi/setup_wizard.go`) generates and displays a key once for the operator to set themselves, but never gains a code path that writes it anywhere on disk — `generatedKey` is a distinct type from anything `config.WriteFile`/`FileConfig` accepts, and this is covered by a regression test (`TestSetupWizard_GeneratedKey_NeverWrittenToConfigFile`). Don't add one.
- **A duration field's disable sentinel is negative, never zero, for every field except `host_grace_period`/`inactivity_timeout`.** `session_idle_timeout`, `session_age_timeout`, `progress_interval`, `sync_snapshot_interval`, `sync_soft_drift`, `sync_hard_drift` reject a literal `0` at config-load time (`config.ValidateDisableableDuration`) — `0` isn't just meaningless for these, it panics `time.NewTicker` for two of them and silently inverts the intended behavior for the rest (see `ARCHITECTURE.md` §16.16). A negative value means disabled; the two party-lifecycle fields keep `0` as a real, immediate-trigger value instead, with `-1` as their own disable sentinel. Adding a tenth duration field (or a new consumer of one of the existing nine) means picking the right shape deliberately and guarding the consuming code against whichever sentinel applies — don't assume `<= 0` is always safe to treat as "disabled" without checking which group the field is in.

## Standing conventions

Practices adopted after concrete failures during the setup-wizard redesign (`ARCHITECTURE.md` §16.14–§16.20). These are working habits, not hard invariants — but each was costly enough in practice to write down.

- **A design-handoff claim must be verified against the live source, never taken from its prose.** When building UI from a design handoff (a design tool's exported prototype plus a README or written description), check every concrete visual/structural claim you're implementing — a dimension, a color, spacing, whether an element exists on a given step — against the prototype's actual rendered or raw source (a computed-style read, a DOM presence check, a source grep). Don't take it from the README's description, even a claim that reads as simple or purely static. This isn't a hypothetical risk: it's been wrong three separate times against the same handoff package — a rail item's blocked-state opacity, a card's `max-width`, and which steps carry an `<h2>` (`ARCHITECTURE.md` §16.15, §16.18) — each time because the claim sounded too simple to bother re-checking.
- **A layout, sizing, or overflow change must be verified against edge-case content, not just the dimensions it targets.** Confirming a fix matches the design source at the specific values you changed isn't sufficient proof it's safe — also verify with content deliberately pushed past the container's boundary: the longest-content step, the smallest supported viewport, any optional/toggle-revealed section. A change that's correct for the values you touched can still silently break a sibling or child element's layout participation elsewhere in the same flex/grid chain. This happened for real: a card-sizing fix that was independently verified correct against the design source still shipped a footer-clipping regression, because giving the card a fixed height and `overflow: hidden` turned a previously invisible gap into a real bug that only surfaced once a step's content was tall enough to hit the new boundary (`ARCHITECTURE.md` §16.19).
- **Before opening a PR that adds a new `ARCHITECTURE.md` subsection, rebase onto current `main` and re-check the section number.** Section numbers collide when parallel sessions each independently plan "the next section after §N" without seeing each other's unmerged work (`ARCHITECTURE.md` §16.19, §16.20 — this required a manual renumber). Immediately before finalizing documentation and opening the PR, not just at the start of the session, pull `main` and confirm the proposed number is still the next unused one there; renumber if something else has landed in the meantime.
- **Never attribute a request, finding, or decision to a specific named individual.** Don't write "John requests..." or "...as John mentioned earlier..." (or any equivalent naming a specific person) in Issues, PRs, commit messages, code comments, or session reports. Refer to the source impersonally instead — "per the approved plan," "per the linked Issue," "the project's stated invariant," and similar.

## Where things live

```
cmd/server/main.go        Process entrypoint: startup-mode dispatch, config load, privdrop, DB open, wiring, graceful shutdown.
internal/config/          Config loading and validation, layered: env var > config.jsonc (/data/config/config.jsonc, JSONC) > hardcoded default. TOKEN_ENCRYPTION_KEY(_FILE) is env-only, never in the file.
internal/dbx/             SQLite schema (migrations/), models, and the data access layer (store.go).
internal/session/         Opaque cookie sessions + synchronizer-token CSRF. No JWTs, no signing secret.
internal/emby/            Emby HTTP client: auth, item metadata, playback URL construction, progress reporting.
internal/party/           The sync engine: one actor goroutine per active party (party.go) + the registry (hub.go).
internal/wsproto/         The WebSocket wire protocol (message types, envelopes, payloads).
internal/httpapi/         HTTP handlers and routing — auth, party REST endpoints, the WS upgrade handler (ws.go).
internal/syncalg/         Pure, unit-tested drift/clock-offset/staleness math — canonical reference, mirrored in JS.
internal/embyreport/      Best-effort per-user Emby playback-progress reporting side channel.
internal/privdrop/        PUID/PGID privilege drop (root → unprivileged) for the distroless container.
internal/webassets/web/   Server-rendered templates + static frontend (JS mirrors internal/syncalg's math).
```

- **Sync hub:** `internal/party/hub.go` (registry, startup recovery, inactivity sweep) + `party.go` (per-party actor, one goroutine per party, all state mutation serialized through it).
- **Emby client:** `internal/emby/client.go` — every call takes the requesting user's own access token; nothing here accepts a shared/service token.
- **Session handling:** `internal/session/session.go` — cookie issuance/validation, CSRF token comparison.
- **Migrations:** `internal/dbx/migrations/*.up.sql` / `*.down.sql` — never edit a shipped migration; add a new one.
- **Startup mode:** `cmd/server/main.go`'s `runLoop()` checks `config.FileExists(configPath)` before anything else, in a loop rather than a single dispatch. Missing → `runSetupRequired()`: the setup wizard (`internal/httpapi/setup_wizard.go`'s `RegisterSetupWizardRoutes`; no DB, no privdrop, no encryption-key requirement). Once the wizard writes the file, the loop attempts `config.LoadFromPath` in-process; if that fails only because `TOKEN_ENCRYPTION_KEY`/`_FILE` isn't set yet, `runAwaitingRestart()` serves a minimal placeholder and waits — the process never exits as part of this transition, on either path (see ARCHITECTURE.md §16.9). Otherwise → `runNormalWithConfig()`, today's full startup path.
- **The three incarnations share one persistent listener, not one each.** `cmd/server/listener.go`'s `connBroker`/`handoff` keep the real `net.Listener` open and continuously accepting across a same-address transition between incarnations — each incarnation's `http.Server.Shutdown` only stops *that* incarnation's own `handoff` from reading further connections, never the underlying socket. Don't reintroduce a close-and-rebind (each incarnation calling `net.Listen` for itself again): that's exactly the race this closed — a real window where nothing is listening on the port at all, which is what broke the setup wizard's own confirmation page loading its CSS (`ARCHITECTURE.md` §16.25). `runLoop`'s `acquireListener` only really closes and rebinds when the desired address changes, or for an explicitly ephemeral `":0"` address.

## Build, test, run

```
go run ./cmd/server                                          # needs env vars from .env.example set (or a config.jsonc — see below)
go build ./...
go test ./...                                                 # unit + integration tests
go test -race ./...
node --test internal/webassets/web/static/js/*.test.mjs       # frontend JS tests: sync math (mirrors internal/syncalg), playlist selection logic, chat validation/truncation, native-pause/ended event forwarding, avatar resolution/caching
docker compose up -d --build                                  # or: podman quadlet, see watchparty.container
```

Copy `.env.example` to `.env` first; `TOKEN_ENCRYPTION_KEY` or `TOKEN_ENCRYPTION_KEY_FILE` (exactly one — `openssl rand -base64 32`, or `./watchparty --generate-key`) is always required via the environment, regardless of `config.jsonc`. Every other setting (`EMBY_SERVER_URL`, `APP_ORIGINS`, etc.) can come from either an env var or `/data/config/config.jsonc` — env wins if both are set; if `config.jsonc` doesn't exist at all, the server starts in **setup-required mode** instead of failing (see `internal/config` and `ARCHITECTURE.md` §16). `internal/privdrop`'s tests that exercise real privilege-drop syscalls only run when `go test` itself runs as root; expect them skipped locally and in most CI.
